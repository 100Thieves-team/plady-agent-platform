## 1. 왜

- 지금 스크립트를 새로 만드는 길은 둘뿐이다. Hermes 초안을 받거나, 레포의 `qa-platform/cases/*.yaml` 을 손으로 고쳐 PR 을 연다.
- 초안 화면에 YAML 을 직접 고쳐 저장하는 칸은 있다. 하지만 어떤 키가 있는지, 본문에 어떤 필드가 들어가는지 알아야 쓸 수 있다.
- 2026-09-23 실패(`r-20260923-090724-c90e`)가 좋은 예다. Hermes 가 ONLINE 룸 생성 본문에 `sigunguId` 를 넣어 E400 이 났다. 사람이 고치려 해도 YAML 을 열어 한 줄을 찾아 지워야 했다. 폼이었다면 입력칸 옆에 스키마 설명 "지역 시군구 id (OFFLINE 일 때)" 가 보이고, 비워 둔 칸은 본문에서 빠진다.
- 근본 원인은 API 명세가 모호한 데 있다(백엔드 쪽 과제). 폼은 사람이 그 모호함을 눈으로 확인하고 고치기 쉽게 해 줄 뿐이다.

## 2. 무엇을 폼으로 다루나 — 범위

플랫폼에는 "테스트 케이스"라 부를 만한 것이 셋 있다. 고정 규칙 "TC 정본은 SSOT·PRD + OpenAPI, 플랫폼은 파생만" 을 지키면 폼으로 다룰 수 있는 범위가 갈린다.

| 대상 | 원본 | 폼으로 추가 | 폼으로 수정 | 폼으로 삭제 |
|---|---|---|---|---|
| **스크립트** (smoke·sanity·manual·setup) | 레포 `cases/*.yaml` | ✅ | ✅ | ✅ |
| **수동 작성 TC** | 레포 `catalog/manual-tc.yaml` | ✅ | ✅ | ✅ |
| **비즈니스 규칙 TC** | llm-wiki `상태-SSOT.yaml` | ❌ | ❌ | ❌ (자동화 제외만) |
| **API 계약 TC** | 백엔드 OpenAPI | ❌ | ❌ | ❌ (자동화 제외만) |

- 비즈니스 규칙 TC 와 API 계약 TC 는 원본이 플랫폼 밖에 있다. 여기서 고치면 다음 파생 때 사라지거나 원본과 어긋난다.
- 그래서 이 둘의 상세 화면에는 폼 대신 **원본을 고치러 가는 링크**(위키 SSOT 항목, 백엔드 REST Docs 절)와 기존 **자동화 제외** 버튼만 둔다.
- **테스트 데이터 만들기 카드**도 suite `setup` 스크립트라 같은 폼으로 만든다. 입력칸(inputs)·돌려줄 값(outputs) 칸이 setup 일 때만 열린다.

## 3. 흐름 — 폼도 초안을 거친다

폼으로 만든 것도 **Hermes 초안과 똑같은 길**을 탄다. 고정 규칙 "승인 없이 실행 스위트에 들어가는 스크립트는 없다" 를 그대로 지킨다.

```
[새 스크립트] 또는 스크립트 상세의 [폼으로 고치기] 또는 [삭제 요청]
  → 폼 작성 → [초안으로 저장]            ← 결정론 검증(기존 drafts.validate) 이 저장 때마다 돈다
  → 초안 화면: [한 번 실행해 보기]        ← 기존 초안 시험 실행
  → [승인]
  → main 에 바로 커밋 (§6 결정, [skip ci])
  → 플랫폼이 그 파일을 바로 다시 읽어 실행 스위트에 들어간다
```

- 초안 목록에서 출처를 구분한다. 기존 `hermes`, `hermes-revise` 에 `form`(새로 만듦), `form-edit`(고침), `form-delete`(삭제 요청)가 더해진다.
- 폼으로 고친 초안은 기존 "바뀐 TC 에 맞게 Hermes 가 고치기" 초안처럼 **현재 스크립트와의 diff** 를 보여 준다.
- **Hermes 초안도 폼으로 연다.** 초안 화면에 [폼으로 고치기] 를 두면, 이번 sigunguId 같은 실수를 YAML 없이 고칠 수 있다.
- 모든 저장·승인·삭제 요청은 감사 로그에 남는다(`draft.form_save`, `draft.delete_request`, 기존 `draft.approve` 등).

## 4. 스크립트 폼

한 화면, 위에서 아래로 기본 정보 → 단계 카드들 → 미리보기 순서다. 화면 오른쪽 위에 **폼 | YAML** 토글을 둔다.

### 4.1 기본 정보

| 칸 | 입력 방식 | 비고 |
|---|---|---|
| 스위트 | smoke · sanity · manual · setup 중 선택 | setup 이면 §4.4 칸이 열린다 |
| 검증하는 TC (covers) | TC 검색 후 선택, 여러 개 | TC 목록 화면에서 고른 TC 로 시작하면 미리 채워진다. setup 은 숨김 |
| id | 자동 제안 `{도메인}.{제목에서 뽑은 영문 슬러그}` 후 수정 가능 | 이미 있는 id 면 저장 전에 경고 |
| 제목·설명 | 텍스트 | |
| 도메인 | 단계의 API 경로에서 자동 계산, 수정 가능 | 기존 `domain_of_path` |
| 출처 | covers 로 고른 TC 의 PRD 절에서 자동, 추가 가능 | |
| 기본 테스트 계정 | 드롭다운 (qa-host, qa-guest, 플랫폼이 만든 QA 회원) | 기존 `all_actors()` |

### 4.2 단계 카드

단계마다 카드 하나. [단계 추가] · [복제] · [위로/아래로] · [삭제] 버튼이 있다.

- **이름**, **테스트 계정**(비우면 기본 계정), **검증하는 TC**(단계별 covers).
- **API 고르기**: API 호출 화면처럼 OpenAPI 에서 검색해 고른다. 메서드·경로가 채워진다.
- **요청**: API 호출 카드의 Normal | Swagger 입력을 그대로 쓴다.
  - Normal 은 스키마 필드마다 입력칸과 **스키마 설명**을 보여 준다. 필수 필드는 표시되고, 선택 필드는 비워 두면 본문에서 빠진다.
  - enum 설명(`ONLINE | OFFLINE` 등)이 있으면 드롭다운으로 만든다.
  - 값 칸에는 변수를 쓸 수 있다. 자동완성 목록에 `{{fixture.*}}`, `{{actor.*}}`, `{{date:+N}}`, `{{rand}}`, 앞 단계에서 저장한 변수가 뜬다.
- **기대 결과**: 러너가 평가하는 5종을 칸으로 푼다.
  - 상태 코드: 스펙의 응답 코드 중 선택하거나 직접 입력.
  - result: SUCCESS · ERROR · 검사 안 함.
  - 오류 코드: 스펙 예시에 나온 코드(E1402 등) 중 선택하거나 직접 입력.
  - 응답 값 검사(json): 행 추가 방식. 경로 · 기대값.
  - 존재 검사(exists): 경로 목록.
- **저장할 값(save)**: 행 추가 방식. 변수 이름 · 응답 경로. 다음 단계의 자동완성에 바로 뜬다.
- **이 단계만 보내 보기**: 지금 입력으로 API 호출 화면을 새 탭에 연다(기존 `/explorer` 프리필). 앞 단계 변수는 치환되지 않으니 직접 넣는다.

### 4.3 폼 | YAML

- **정본은 폼 쪽 구조 하나**다. 저장하면 서버가 기존 스크립트 YAML 형식으로 바꿔 초안에 넣는다.
- YAML 탭은 서버가 만든 결과를 보여 준다. YAML 을 직접 고치고 싶으면 기존 초안 YAML 칸을 쓴다.
- 폼 ⇄ YAML 양방향 동기화는 하지 않는다. 브라우저에 YAML 파서를 넣어야 하고, 폼이 표현 못 하는 형태가 생기면 값이 사라진다.
- 기존 스크립트를 폼으로 열 때는 서버가 YAML 을 읽어 폼 구조로 넘긴다. 러너가 아는 키만 있으므로 폼으로 전부 표현된다. 표현 못 하는 키가 있으면 폼을 열지 않고 "YAML 로 고쳐 달라" 고 안내한다.

### 4.4 setup 전용 칸

- **화면 입력칸(inputs)**: 행 추가 방식. 이름 · 라벨 · 기본값 · 필수 · 도움말. 값 칸 자동완성에 `{{input.이름}}` 이 뜬다.
- **끝나면 보여 줄 값(outputs)**: 저장할 값(save) 이름 중에서 고른다.

### 4.5 전제 카드 (`uses`)

- 기본 정보의 **전제 카드** 드롭다운에서 테스트 데이터 만들기 카드 하나를 고른다. 그 카드의 단계가 스크립트 앞에 붙어 먼저 돈다([qa-platform-scenarios.md](qa-platform-scenarios.md) §8).
- 고르면 카드의 입력칸이 표로 뜬다. 비우면 카드 기본값이다. 카드의 결과값(outputs)이 변수 자동완성에 뜨고, setup 카드라면 끝나면 보여 줄 값의 선택지에도 들어간다.

## 5. 수동 작성 TC 폼

`catalog/manual-tc.yaml` 한 항목을 칸으로 푼다.

| 칸 | 입력 방식 |
|---|---|
| PRD 문서 · 절 | 위키 PRD 목록에서 선택, 절 번호 입력. 고르면 절 본문이 옆에 보인다 |
| id | `PRD.{문서}.{절}#{다음 번호}` 자동. 운영 기준이면 `OPS.{영역}.{이름}#{n}` |
| 도메인 · 제목 | 도메인 선택, 제목 텍스트 |
| given · when · then | 텍스트 3칸 |
| 관련 API | OpenAPI 검색 후 선택, 여러 개 |

- 저장하면 기존 "수동 TC 제안" 초안(kind `tc`)이 된다. 검증은 기존 `validate_manual_tc` 를 쓴다.
- **삭제**: 이 TC 를 covers 로 가리키는 스크립트가 있으면 삭제 요청을 막고 그 스크립트 목록을 보여 준다. 먼저 스크립트의 covers 에서 빼야 한다.

## 6. 레포 반영 — 결정이 필요한 곳

스크립트와 수동 TC 는 레포에 있고 **이미지에 구워져 배포된다**(`docker/qa-platform.Dockerfile` 의 `COPY qa-platform/cases`). 지금은 승인 뒤 사람이 YAML 을 복사해 PR 을 연다. 세 가지 방식이 있다.

| 방식 | 승인하면 | 좋은 점 | 나쁜 점 |
|---|---|---|---|
| **A. 플랫폼이 PR 을 연다** (권장) | 플랫폼이 이 레포에 브랜치를 만들고 파일을 고쳐 PR 을 연다. 머지·배포 뒤 반영 | git 리뷰·이력이 그대로. 레포가 계속 유일한 원본 | 이 레포에 쓰기 권한이 있는 토큰이 필요(§8). 반영까지 머지·배포 시간 |
| B. 플랫폼에 바로 반영 | 플랫폼 볼륨에 저장하고 즉시 실행 스위트에 넣는다 | 가장 빠르다 | 레포와 실행 중인 스크립트가 갈라진다. 원본이 둘이 된다 |
| C. 지금처럼 복사 | 초안 화면에 [YAML 복사] · [파일 받기] 버튼. 사람이 PR | 추가 권한 없음 | 손이 많이 간다. 복사 실수 |

- **결정 (2026-09-23 사용자 "그냥 커밋 푸시해")**: PR 없이 **main 에 바로 커밋**한다(A 의 변형). 커밋 메시지에 `[skip ci]` 를 붙여 YAML 한 줄 때문에 플랫폼 전체가 재배포되지 않게 하고, 플랫폼은 커밋한 파일을 자기 사본에 바로 쓰고 다시 읽는다. 토큰이 없을 때는 C 로 떨어진다.
- 커밋은 사람이 승인 버튼을 눌렀을 때만 일어난다. "실행 시작은 사람" 규칙과 맞는다. 아래 §6.1·§8 의 PR 관련 줄은 설계 1판 기록이다.

### 6.1 A 방식의 파일 고치기

- 한 파일에 스크립트가 여러 개이고 주석이 있다. 파일 전체를 다시 쓰면 주석과 순서가 날아간다.
- 그래서 **해당 항목의 텍스트 구간만 바꾼다.** `  - id: {id}` 줄부터 다음 `  - id:` 줄 앞까지를 새 YAML 블록으로 교체한다.
- 새 스크립트는 도메인 파일(`cases/{도메인}.yaml`) 끝에 붙인다. 파일이 없으면 새로 만든다.
- 삭제는 그 구간을 지운다.
- 바꾼 파일 전체를 다시 불러 검증(`load_dir`)하고 통과할 때만 PR 을 연다.
- PR 제목은 `qa(cases): {id} 추가|수정|삭제 — {담당자}`, 본문에는 초안 id, 시험 실행 id와 결과, 검증하는 TC 를 적는다.
- 같은 스크립트에 열린 PR 이 이미 있으면 새로 열지 않고 그 PR 링크를 보여 준다.

## 7. 구현 순서

| 단계 | 내용 | 사람 작업 |
|---|---|---|
| E1 | 스크립트 폼: 새로 만들기 · 기존 스크립트/초안 폼으로 고치기 → 초안 저장. §4 전부. 레포 반영은 C(복사·파일 받기) | 없음 |
| E2 | 삭제 요청 초안 · 수동 작성 TC 폼(§5) · 규칙/계약 TC 상세의 원본 링크 | 없음 |
| E3 | 승인 시 PR 자동 생성(§6 A) | 토큰 발급·SSM 등록 |

E1 만으로도 이번 sigunguId 같은 수정을 YAML 없이 할 수 있다.

## 8. 필요한 것 (A 방식)

- 이 레포(`100Thieves-team/plady-agent-platform`)에 **contents: write, pull_requests: write** 권한이 있는 토큰. fine-grained PAT 나 GitHub App 설치 토큰.
- SSM 파라미터로 넣고 compose 에 `QA_REPO_TOKEN` 으로 전달. 기존 `QA_GITHUB_TOKEN`(백엔드 레포 읽기)과 분리한다.
- 브랜치 이름 `qa-cases/{초안 id}`. main 보호 규칙은 그대로 둔다.

## 9. 하지 않는 것

- 비즈니스 규칙 TC·API 계약 TC 를 플랫폼에서 고치기(§2).
- 폼 ⇄ YAML 양방향 동기화(§4.3).
- 승인 없이 실행 스위트에 넣기, PR 자동 머지.

## 10. 검토 질문과 답 (2026-09-23)

1. **범위** — 폼 편집은 스크립트와 수동 작성 TC 만, SSOT·OpenAPI 에서 오는 TC 는 원본 링크와 자동화 제외만. → **맞다.**
2. **레포 반영** — → **"그냥 커밋 푸시해"**: PR 없이 main 에 바로 커밋(§6 결정).
3. **승인 조건** — 한 번 실행해 보기 통과를 승인 조건으로 할까? → **"테스트 코드 정도로 검증하면 충분"**: 저장·승인 때 결정론 검증(형식·TC 대조·테스트 계정·픽스처·본문 스키마)만 한다. 시험 실행은 선택.
