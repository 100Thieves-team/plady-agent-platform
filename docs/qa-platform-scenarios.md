# QA 플랫폼 — 사용자 시나리오로 테스트 관리하기 (설계)

> 용어(2026-09-24 사용자 결정): 이 문서의 **케이스**는 예전 판의 "변형", **테스트 조건**은 예전 "테스트 케이스(TC)" 다. 코드의 키 `variant:`, id 앞머리, URL 은 그대로다.
> 상태: **설계 3판 확정 (2026-09-24), 구현 중.** 검토 답은 §16, 구현 기록은 §17. 1단계(초안·승인 없애기), 2단계(PRD 2장 구체화, 백엔드 기준 동기화), 3단계(전제 재사용), 4단계(시나리오 읽기), 5단계(시나리오 폼), 6단계(Hermes 변형 채우기·변형에서 스크립트)가 끝났다. 다음은 7단계(실행과 드리프트, Hermes 로 다시 맞추기 포함).
> 사용자 요청: "스크립트 기반은 너무 비직관적이다. 단일 정책은 결국 유즈케이스 안의 여러 로직 중 하나다. 시나리오는 AI 가 만들고, 사람이 CRUD 를 직접 다 할 수 있게 하자."
> 관련: [qa-platform-tc.md](qa-platform-tc.md)(TC 카탈로그), [qa-platform-editor.md](qa-platform-editor.md)(폼 편집, 이번에 저장 흐름이 바뀐다), [qa-platform-progress.md](qa-platform-progress.md)(Hermes 작업 SSE), [policy-ssot-split.md](policy-ssot-split.md)(PRD 요구 id, 게이트 검사 key).

## 1. 왜

- 지금 관리 단위는 **스크립트**다. 무엇을 한 스크립트에 묶을지는 쓴 사람 마음이다. `room.create-and-cancel` 은 이름 하나에 정상 생성, 취소, 재취소 거절이 섞여 있어 이름만 보고는 무엇을 확인하는지 알 수 없다.
- 정책 하나는 혼자 서 있지 않다. "최소 인원 미달이면 확정 거절" 은 룸 생성, 신청, 수락, 확정이 이어져야 드러난다. 정책은 유즈케이스 흐름 안의 한 분기다.
- 토스 QA 사례처럼 **사용자 흐름 하나를 두고 분기점마다 케이스를 나열**하면 사람이 기능을 이해하는 방식과 같아진다. 실행도 "어느 케이스를 돌릴까" 로 고르게 된다.
- 재료는 이미 있다. PRD 11개 모두 2장에 `### 시나리오 S1` 이 있고 규칙 줄마다 요구 id `R{n}` 가 있다. 규칙표 게이트 검사 194개에는 key 가 있고, 그중 93개에는 백엔드 ErrorCode 가 적혀 있다.

## 2. 구조 — 다섯 층

| 층 | 무엇 | 원본 | 예 |
|---|---|---|---|
| **기능** | PRD 문서 하나 | 위키 `raw/product/<PRD>.md` | 룸 생성 |
| **시나리오** | 사용자가 결과 하나를 얻기까지 여러 행동을 잇는 흐름 | **PRD 2장 `시나리오 Sn`**. QA 는 1:1 로 따른다 | S1 참가를 신청하고 방장이 참여자를 구성한다 |
| **케이스** | 흐름의 한 갈래 | 정상 흐름, PRD 분기, 규칙표 거절 규칙, 사람이 더한 것 | 최대 인원이 최소 인원보다 작으면 E1402 |
| **단계** | API 호출 하나 | 스크립트의 steps (지금과 같다) | POST /v1/rooms |
| **테스트 조건** | 확인할 조건 하나 | 지금의 테스트 조건 목록 (지금과 같다) | `G.room.create#headcount-range` |

- **시나리오는 PRD 가 정한다.** QA 는 PRD 시나리오를 나누거나 합치지 않는다. 그래서 "QA 시나리오 몇 번이 PRD 어디까지인가" 를 잇는 칸이 없다. 시나리오가 모자라면 PRD 를 고친다(§3).
- **QA 가 더하는 것은 케이스다.** 케이스 목록과 케이스를 구현하는 스크립트가 QA 몫이다.
- **스크립트는 케이스 하나를 구현한다.** 스크립트에 `variant:` 칸이 생긴다.
- 실행기의 단계 실행, 테스트 조건 카탈로그, 실행 기록은 바뀌지 않는다. 실행기에는 전제 재사용(§8)만 더해진다.

### 2.1 케이스의 종류

| kind | 화면 이름 | 어디서 나오나 |
|---|---|---|
| `happy` | 정상 흐름 | 시나리오마다 하나 이상 |
| `branch` | 분기 | PRD 2장의 `분기:` 줄 |
| `reject` | 거절 | 규칙표 게이트 검사 하나. 예: `G.room.create#headcount-range` |
| `extra` | 추가 | 사람이 더한 경계값, 회귀 사례 |

- 거절 케이스는 **검사 하나에 케이스 하나**가 기본이다. `headcount-range` 처럼 한 검사가 규칙 셋을 품으면 케이스를 셋으로 나눌 수 있다.
- 케이스마다 **확인 방식**이 있다. `auto` 는 스크립트로 확인하고, `manual` 은 사람이 확인한다.

### 2.2 아직 테스트가 없는 거절 조건

1판에서 "거절 변형 후보", 3판에서 "테스트 없는 거절 규칙" 이라고 부른 것이다. 이름이 모호해서 바꾼다.

- 규칙표에는 기능마다 "이러면 거절한다" 는 규칙이 적혀 있다. 룸 생성에는 17개가 있고, 그중 하나가 "최대 인원이 최소 인원보다 작으면 E1402" 다.
- 이 규칙마다 거절 케이스가 하나씩 있어야 빠짐없이 테스트한 것이다.
- **아직 테스트가 없는 거절 조건**은 시나리오 단계에 걸린 게이트의 검사 중 아직 어느 케이스도 확인하지 않는 것이다. 자동화 제외 목록에 있는 것은 뺀다.
- 플랫폼이 AI 없이 계산한다. 시나리오 화면에 "아직 테스트가 없는 거절 조건 N개" 로 뜨고, 줄마다 [케이스로 추가] 버튼이 폼을 미리 채워 연다.
- 규칙 수가 곧 할 일의 크기다.

| 기능 | 게이트 검사 | ErrorCode 있음 |
|---|---|---|
| 룸 생성 | 22 | 17 |
| 룸 탐색 | 11 | 0 |
| 룸 참여 및 참여자 관리 | 29 | 20 |
| 룸 진행 확정 | 7 | 4 |
| 룸 진행 준비 | 27 | 20 |
| 룸 진행 | 31 | 6 |
| 룸 진행 마무리 및 출석 | 12 | 3 |
| 룸 방명록 | 8 | 3 |
| 유저 후기 및 신뢰 관리 | 18 | 8 |
| 회원 및 프로필 | 29 | 12 |
| 운영자 관리 | 규칙표 조각 없음 | |

- ErrorCode 가 없는 101개 중 24개는 `catalog/bindings.yaml` 에 ErrorCode 를 채워 두었다. 나머지 77개는 화면에서만 막는지, 백엔드가 E400 으로 막는지, 아예 안 막는지 문서로는 모른다. 목록에 보이되 `manual` 로 시작한다(§16 3차).

## 3. PRD 2장 구체화 (위키 작업)

지금 PRD 는 모두 `시나리오 S1` 하나뿐이고, 4장에 있는 기능 상당수가 2장 흐름에 나오지 않는다. 예를 들어 회원 PRD 의 S1 은 가입과 복귀만 다루고 이력서 보관, 프로필 수정, 탈퇴는 빠져 있다.

### 3.1 PRD 시나리오와 규칙표는 역할이 다르다

잘게 나누면 PRD 시나리오가 규칙표와 같아진다. 규칙표의 명령(command)이 이미 "룸 취소", "질문 삭제", "로그아웃" 처럼 행동 하나 단위이기 때문이다. 2판 제안 29개 중 상당수가 명령 하나짜리였다. 그래서 3판은 나누지 않는 쪽을 기본으로 한다.

| | PRD 2장 시나리오 | 규칙표 (SSOT) | QA 케이스 |
|---|---|---|---|
| 답하는 질문 | 사용자가 무엇을 이루려고 어떤 순서로 움직이나 | 행동 하나를 언제, 누가 할 수 있나 | 이 흐름의 이 단계에서 이 규칙에 걸리면 어떻게 되나 |
| 단위 | 여러 행동을 잇는 흐름 | 행동 하나(명령)와 그 조건(게이트) | 흐름 × 규칙의 한 칸 |
| 크기 | 기능당 1~2개 | 기능당 명령 0~12개 | 규칙 수만큼 |

- 두 원본이 서로 다른 축이라서, 그 곱이 QA 케이스가 된다. PRD 시나리오가 명령 단위로 쪼개지면 이 곱이 사라지고 규칙표를 한 번 더 적은 것이 된다.

### 3.2 규칙

- **시나리오는 흐름이다.** 명령 하나로 끝나는 것은 시나리오가 아니다. 기존 시나리오의 단계나 `분기:` 줄로 넣는다.
- **행위자는 여럿이어도 된다.** 신청자가 신청하고 방장이 수락하는 것처럼 한 흐름에 여러 사람이 나온다. 단계마다 누가 하는지 적는다.
- **새 시나리오는 흐름이 따로 설 때만 만든다.** 기존 흐름의 결과를 전제로 하지 않고 다른 목표로 시작하는 경우다. 기능당 1~2개를 넘지 않게 한다.
- **규칙표의 사람 명령은 2장 어딘가에 한 번은 나온다.** 단계든 분기든 된다. 시스템이 혼자 하는 명령은 빼도 된다. 이 조건이 있어야 QA 트리에서 빠지는 명령이 없다.
- **조건과 거절은 2장에 쓰지 않는다.** "최대 인원이 최소 인원보다 작으면" 같은 것은 규칙표와 4장 몫이다. 2장이 그것까지 적으면 규칙표와 겹친다.
- **새 내용을 지어내지 않는다.** 단계 문장은 3장, 4장에 이미 있는 내용을 흐름으로 옮긴 것이다. 어긋나는 게 보이면 고치지 않고 `> ❓` 로 표시한다.
- **기존 줄은 그대로 둔다.** 이미 있는 `R1`~`Rn` 줄은 문장을 바꾸지 않는다. 문장을 바꾸면 그 요구를 인용한 SSOT 레코드에 드리프트 알림이 뜨기 때문이다.
- **새 줄에는 새 요구 id 를 붙인다.** 머리말 `next_req` 에서 번호를 받고 재사용하지 않는다.
- 이 규칙은 team-wiki-v2 `AGENTS.md` 의 PRD 절에 더한다. 편집은 에이전트가 한다.

### 3.3 고칠 곳 제안

대부분 S1 에 단계나 분기를 더하는 일이다. 새 시나리오는 셋이다.

| 기능 | 지금 S1 에 빠진 사람 명령 | 제안 |
|---|---|---|
| 룸 생성 | 일괄 생성, 모집 중 수정, 취소 | S1 에 일괄 생성 분기. **S2 방장이 모집 중인 룸을 고치거나 취소한다** (만든 뒤 따로 시작하는 흐름) |
| 룸 탐색 | 명령 없음 | S1 끝에 "내 면접" 분기 |
| 룸 참여 및 참여자 관리 | 없음 | 그대로. 철회, 반려, 재신청을 분기로 적을지만 본다 |
| 룸 진행 확정 | 없음 | 그대로. 확정 뒤 일정 변경을 분기로 더한다 |
| 룸 진행 준비 | 꼬리질문, 삭제 | S1 에 분기 둘 |
| 룸 진행 | 질문 체크, 답변 요약, 댓글, 클로징 평가 | S1 단계에 행동을 붙인다 |
| 룸 진행 마무리 및 출석 | 없음 | 그대로 |
| 룸 방명록 | 없음 | 그대로 |
| 유저 후기 및 신뢰 관리 | 건너뛰기, 수정, 삭제, 신고 | S1 에 분기. **S2 받은 후기를 보고 신고한다** |
| 회원 및 프로필 | 로그아웃, 프로필 수정, 탈퇴, 이력서 넷 | **S2 마이페이지에서 프로필과 이력서를 관리한다** (로그아웃, 탈퇴는 분기) |
| 운영자 관리 | 규칙표 조각 없음 | 그대로 |

- 시나리오는 모두 14개가 된다. 2판 제안은 29개였다.
- **MVP 범위(2026-09-23 팀 허들):** 룸 진행 준비와 룸 진행은 이번 MVP 에서 빠졌다. PRD 는 유지하되 QA 시나리오 파일은 만들지 않고, 두 기능의 테스트 조건은 `catalog/exclusions.yaml` 에 "MVP 범위 밖" 으로 뺀다(§17.3).
- 운영자 전용 명령(이용 제한, 후기 숨김)은 자동화 제외라 운영자 관리 PRD 에 두고 여기서는 뺀다.

### 3.4 절차

1. 에이전트가 위키 worktree 에서 PRD 11개의 2장을 고친다. AGENTS.md 규칙도 같은 커밋에 넣는다.
2. 정책 렌더러와 드리프트 검사를 로컬에서 돌려, 기존 요구의 문장이 바뀌지 않았는지 확인한다. 바뀐 요구가 0개여야 한다.
3. 변경 요약을 사용자에게 보여 주고 확인을 받은 뒤 위키 main 에 반영한다.

## 4. 어디에 두나 (확정)

**이 레포 `qa-platform/scenarios/<기능>.yaml`.**

- 시나리오 파일은 PRD 시나리오를 **인용**하고 케이스를 **더한다**. 기획 원본이 아니라 테스트 설계다.
- 스크립트(`cases/`)와 같은 곳이라 저장 흐름(§9), 이미지에 굽기, 시작할 때 sync 를 그대로 쓴다.
- 파일 이름은 위키 조각 `기능/<PRD>.yaml` 과 같게 한다.

## 5. 파일 형식

```yaml
# qa-platform/scenarios/룸-생성.yaml
feature: 룸 생성                  # PRD 문서 이름
scenarios:
  - id: S1                        # PRD 2장 시나리오 번호와 같다. 제목과 단계는 PRD 에서 읽는다
    actor: qa-host                # 기본 테스트 계정
    gates:                        # 단계 요구 id 에 걸리는 게이트. 테스트 없는 거절 규칙이 여기서 나온다
      R6: [G.room.create]
    variants:
      - key: happy
        kind: happy
        title: 온라인 룸을 만들면 모집 중으로 열린다
        given: 활성 룸이 없는 방장
        then: 200, 상태 RECRUITING, 상세의 방장이 본인이다
        checks: [C.room.create, op.createRoom:200]
      - key: pasted-posting
        kind: branch
        at: R3
        title: 목록에 없는 공고는 링크를 붙여 그 자리에서 만든다
        mode: manual
      - key: headcount-range
        kind: reject
        at: R6
        title: 최대 인원이 최소 인원보다 작으면 E1402 로 거절된다
        given: minParticipants 4, maxParticipants 2
        then: 400 E1402, 룸이 만들어지지 않는다
        checks: [G.room.create#headcount-range]
    basis_hash: 3f9a1c            # 저장할 때 플랫폼이 계산. §10
```

- **시나리오 제목과 단계는 파일에 없다.** PRD 2장에서 읽어 화면에 보인다. 1판의 `steps` 칸은 PRD 가 구체화되면서 필요 없어졌다.
- **`at`:** 분기·거절이 일어나는 단계다. PRD 2장 단계의 요구 id 로 적는다.
- **`gates`:** 단계 요구 id 별로 걸리는 게이트다. Hermes 가 채우고 사람이 고친다.
- **전체 id:** `기능/시나리오/변형` 이다. 예: `룸-생성/S1/headcount-range`. 스크립트는 `variant: 룸-생성/S1/headcount-range` 로 가리킨다.
- **케이스 key:** 거절 케이스는 검사 key 를 그대로 쓴다. 한 시나리오 안에서 겹치면 게이트 이름을 앞에 붙인다. 예: `create.login-required`.
- **`checks`:** 이 케이스가 확인해야 하는 테스트 조건이다. 스크립트의 covers 가 이것을 포함해야 한다.
- **상태는 저장하지 않는다.** 자동화됨, 사람이 확인, 제외, 테스트 없음은 스크립트와 제외 목록을 보고 매번 계산한다.

## 6. 누가 무엇을 채우나

| 일 | 누가 |
|---|---|
| 시나리오와 단계 | PRD (위키) |
| 단계에 걸리는 게이트 | Hermes 가 채우고 사람이 고친다. 게이트 68개 중 36개는 명령과 이름이 짝이라 결정론으로 먼저 제안한다 |
| **아직 테스트가 없는 거절 조건** | **플랫폼이 계산** |
| 케이스 제목, 전제, 기대 결과 | Hermes 가 채우고 사람이 고친다. 재료는 검사의 ref, message, error, note |
| 케이스 상태 | **플랫폼이 계산** |
| 근거 변경 표시 | **플랫폼이 계산** |

### 6.1 결정론 검증

저장할 때마다 돈다. 폼으로 저장하든 Hermes 가 저장하든 같다. 오류는 저장을 막고, 경고는 보여만 준다.

- **오류:**
  - 시나리오 id 가 PRD 2장에 없다.
  - `at` 이나 `gates` 의 요구 id 가 그 시나리오의 단계에 없다.
  - 게이트나 checks 의 테스트 조건이 없다. 옛 번호 id 는 별칭으로 풀어 받는다.
  - 케이스 key 가 겹친다.
  - 스크립트의 `variant:` 가 없는 케이스를 가리킨다.
- **경고:**
  - 거절 케이스의 checks 가 `at` 단계의 gates 밖에 있다.
  - 한 케이스가 검사 여러 개를 확인한다.
  - 한 케이스를 스크립트 둘 이상이 구현한다.
  - 스크립트의 covers 가 케이스의 checks 를 다 담지 않았다.

## 7. Hermes

모두 사람이 버튼을 눌러 시작한다. 기존 Hermes 작업 틀(`qa/jobs.py`)에서 돌아서 진행 카드와 SSE 가 그대로 붙는다.

- **[Hermes 로 케이스 채우기]:** 기능 화면에 둔다. 작업 kind 는 `scenario` 다.
  - 입력은 PRD 2장 원문과 요구 id, 그 기능의 규칙표 조각(gates, commands, transitions), bindings, 제외 목록, OpenAPI 요약, 지금 시나리오 파일, 아직 테스트가 없는 거절 조건이다.
  - 출력은 그 기능의 시나리오 파일 전체다.
  - §6.1 검증을 통과하면 **바로 저장**한다(§9). 실패하면 오류를 붙여 한 번 더 묻고, 그래도 실패하면 작업이 실패로 끝나고 저장하지 않는다.
- **[Hermes 로 다시 맞추기]:** 근거가 바뀐 시나리오(§10)에 둔다. 바뀐 문장과 지금 파일을 주고 고친 판을 받아 저장한다.
- **[Hermes 로 스크립트 만들기]:** 케이스 화면에 둔다. 기존 스크립트 생성을 쓰되, 입력에 케이스의 제목, 전제, 기대 결과, checks, 쓸 만한 테스트 데이터 만들기 카드(§8)를 더한다. 결과 스크립트에는 `variant:` 가 채워진다.
- Hermes 가 저장한 항목에는 `written_by: hermes` 가 붙는다. 화면에 "Hermes 작성" 표시가 뜨고, 사람이 폼으로 한 번 저장하면 사라진다.

## 8. 전제 재사용 (`uses:`)

### 8.1 문제

"최소 인원 미달이면 진행 확정 거절" 을 확인하려면 룸 생성, 신청, 수락을 먼저 해야 한다. 지금은 스크립트마다 이 준비 단계 4~5개를 전부 적는다. 확정 기능의 거절 케이스가 여럿이면 같은 준비 단계가 여러 스크립트에 복사된다. 요청 본문이 바뀌면 복사본을 전부 고쳐야 한다.

그 준비 과정은 이미 **테스트 데이터 만들기 카드**(suite `setup`)로 있다. `setup.room-open`, `setup.room-with-application`, `setup.room-confirmed` 같은 것들이다.

### 8.2 형식

```yaml
- id: room.confirm-under-min
  title: 최소 인원이 모이지 않으면 진행 확정이 E1431 로 거절된다
  suite: sanity
  variant: 룸-진행-확정/S1/min-participants
  actor: qa-host
  uses:
    setup: setup.room-with-application      # 이 카드의 단계를 먼저 돈다
    with: { title: "[QA] 확정 거절" }         # 카드 입력칸. 안 적으면 기본값
  steps:
    - name: 수락 없이 바로 확정
      covers: ["G.room.confirm#min-participants"]
      request: { method: POST, path: "/v1/rooms/{{roomId}}/confirmation" }   # roomId 는 카드의 outputs
      expect: { status: 409, error_code: E1431 }
    - name: 정리
      request: { method: POST, path: "/v1/rooms/{{roomId}}/cancellation" }
      expect: { status: 200 }
```

- 예시의 경로와 ErrorCode 는 설명용이다.
- `uses` 는 카드 하나만 받는다. 카드끼리도 `uses` 를 쓸 수 있다. 예를 들어 `setup.room-confirmed` 가 `setup.room-with-application` 을 쓰면 카드끼리의 중복도 사라진다. 순환은 검증에서 막는다.
- 카드의 `outputs` 가 스크립트의 변수가 된다. 위 예의 `{{roomId}}` 다.

### 8.3 실행

- **스크립트를 읽을 때 펼친다.** 로더가 카드의 단계를 입력값을 박은 채 스크립트 단계 앞에 붙이고, 각 단계에 `given: setup.room-with-application` 표시를 단다. 실행기의 단계 실행 코드는 그대로다.
- 실행 기록의 스냅샷에는 펼친 단계가 남는다. 나중에 카드가 바뀌어도 그때 무엇을 돌렸는지 보인다.
- **전제 단계가 실패하면 판정은 `error` 다.** 메시지는 "전제 준비 실패: 참가자가 신청 단계에서 409" 처럼 적는다. 확인하려던 규칙이 틀린 것(`fail`)과 구분하기 위해서다.
- 전제 단계는 covers 가 없으므로 테스트 조건 커버리지에 들어가지 않는다.
- 실행 결과 화면에서 전제 단계는 접어서 보인다.
- 폼의 기본 정보에 "테스트 데이터 만들기 카드" 드롭다운과 입력칸이 생긴다. 고르면 카드의 outputs 가 변수 자동완성에 뜬다.

## 9. 저장 흐름 — 초안과 승인을 없앤다 (확정)

스크립트, 수동 작성 테스트 조건, 시나리오 모두 같다.

- **폼 저장:** §6.1 과 기존 스크립트 검증을 통과하면 바로 main 에 커밋되고 플랫폼에 반영된다.
- **Hermes 생성과 고치기:** 검증을 통과하면 바로 저장된다. "Hermes 작성" 표시가 붙는다.
- **삭제:** 확인 창 하나를 거쳐 바로 커밋한다. 시나리오나 케이스를 지울 때는 그것을 가리키는 스크립트 목록을 확인 창에 보인다. 스크립트는 지우지 않고 "시나리오에 연결되지 않은 스크립트"로 남긴다.
- **저장 전에 해 보기:** 폼에 [저장 전에 한 번 실행해 보기] 를 둔다. 지금 초안 시험 실행과 같은 기능이다.
- **되돌리기:** git 이력으로 한다. 스크립트와 시나리오 화면에 최근 커밋 몇 개를 링크로 보인다. 되돌리고 싶으면 그 판을 폼으로 열어 저장한다.
- **감사 로그:** `case.save`, `case.delete`, `scenario.save`, `scenario.delete`, `manual_tc.save`, `manual_tc.delete` 에 커밋 sha 를 남긴다. Hermes 저장은 누른 사람을 operator 로 남긴다.
- **초안 목록 화면(`/drafts`)은 없앤다.** 지금 남은 초안은 옮기는 날 한 번 목록으로 보여 주고 정리한다. drafts 테이블은 기록으로 남긴다.
- **토큰이 없는 환경:** 저장 대신 기존 [반영된 파일 받기] 로 끝난다.
- **실행은 여전히 사람이 시작한다.** Hermes 가 저장한 스크립트도 누군가 실행을 눌러야 돈다.

## 10. 드리프트 — 근거가 바뀌면

- 저장할 때 `basis_hash` 를 계산한다. 그 시나리오 PRD 단계 문장, `at` 과 `gates` 의 요구 문장, checks 검사 정의의 해시다.
- 지금 값과 다르면 시나리오와 케이스에 **"근거가 바뀜"** 표시가 붙는다. 어느 요구 id 의 문장이 어떻게 바뀌었는지 전후를 보인다. [Hermes 로 다시 맞추기] 와 [폼으로 고치기] 가 옆에 있다.
- 검사나 요구 id 가 사라지면 **오류** 표시다.
- PRD 에 새 시나리오가 생기면 트리에 "케이스 없음" 으로 나타난다. 새 검사가 생기면 아직 테스트가 없는 거절 조건에 나타난다.
- 자동으로 고치지는 않는다.

## 11. 실행

- 트리에서 케이스를 체크하고 [고른 케이스 실행] 을 누른다. 기능이나 시나리오를 통째로 고를 수도 있다. 플랫폼은 케이스를 구현한 스크립트 id 목록으로 바꿔 기존 `create_run` 을 부른다.
- 실행 결과와 위키 보고서는 기능, 시나리오, 케이스 순서로 묶는다. 시나리오에 연결되지 않은 스크립트는 끝에 따로 둔다.
- 스위트 실행(smoke, sanity)은 그대로 둔다.

## 12. 화면

- **첫 화면:** 지금 대시보드를 그대로 두고 그 아래에 기능, 시나리오, 케이스 트리를 붙인다 (확정).
  - 기능 줄마다 케이스 수, 자동화됨, 사람이 확인, 제외, 테스트 없음, 아직 테스트가 없는 거절 조건 수, 최근 결과를 막대로 보인다.
  - 펼치면 시나리오, 다시 펼치면 케이스가 나온다. 케이스 줄에 체크박스가 있어 바로 실행할 수 있다.
- **기능 화면 `/features/<기능>`:** 시나리오마다 PRD 단계가 요구 id 와 함께 나오고 케이스 표가 이어진다. 그 아래 아직 테스트가 없는 거절 조건과 [케이스로 추가] 가 있다. [Hermes 로 케이스 채우기] 가 위에 있다.
- **케이스 화면 `/features/<기능>/<시나리오>/<변형>`:** 근거 문장, 전제, 기대 결과, 확인할 테스트 조건, 구현한 스크립트, 실행 이력, 최근 커밋이 보인다. 버튼은 [폼으로 고치기], [스크립트 만들기 (폼)], [Hermes 로 스크립트 만들기] 다.
- **스크립트 목록**은 남긴다. 각 줄에 케이스 이름이 붙고, `variant:` 없는 것은 "시나리오에 연결되지 않은 스크립트"로 모인다.
- **테스트 조건 상세**에 "이 테스트 조건을 확인하는 케이스"가 더해진다. **API 별로 모아 보기**도 그대로다.

## 14. 구현 순서

1. **저장 흐름 바꾸기:** 초안과 승인을 없애고 바로 저장한다. 이미 배포된 폼 편집에 먼저 적용한다. (완료, §17.1)
2. **PRD 2장 구체화:** 위키 작업. §3.3 대로 사용자 확인을 받고 반영한다. (완료, §17.2·§17.3)
3. **전제 재사용:** `uses` 로더 펼치기, 검증, 판정, 폼 칸. setup 카드끼리의 중복도 줄인다. (완료, §17.4)
4. **시나리오 읽기:** 파일 형식, 로더, §6.1 검증, 아직 테스트가 없는 거절 조건 계산, 스크립트 `variant:`, 첫 화면 트리, 기능 화면, 케이스 화면. 룸 생성과 룸 참여 두 기능 파일과 §13 옮기기도 여기에 넣는다. (완료, §17.5)
5. **시나리오 폼:** 케이스 만들기, 고치기, 지우기. (완료, §17.6)
6. **Hermes:** 케이스 채우기, 케이스에서 스크립트 만들기. (완료, §17.7) 다시 맞추기는 근거 변경(basis_hash)이 있어야 누를 수 있어 7단계로 옮겼다.
7. **실행과 드리프트:** 케이스 골라 실행, 결과와 보고서 묶기, basis_hash 비교 표시, [Hermes 로 다시 맞추기].

단계마다 테스트를 더하고 커밋을 따로 한다. 2 는 위키 레포, 나머지는 이 레포다.

### 17.4 3단계 — 전제 재사용 `uses:` (2026-09-24)

- **형식:** `uses: {setup: 카드 id, with: {입력: 값}}`. 줄여서 `uses: setup.room-open` 도 된다. 받는 것은 suite `setup` 카드 하나다. `with` 를 비우면 카드의 기본값을 쓴다. YAML 에서 온 숫자·불린은 그대로, 문자열은 카드 기본값의 타입을 따른다.
- **펼치기:** `cases.load_dir` 가 파일을 다 읽은 뒤 `expand_all` 로 펼친다. 카드 단계에 입력을 박고(`_bake`, `bake_inputs` 와 같은 치환) 스크립트 단계 앞에 붙인다. 각 전제 단계에는 `given: 카드 id` 가 붙고, 카드의 actor 가 박히고, covers 는 비운다. `Case.raw` 와 `to_yaml()` 은 파일 모양 그대로라 폼·Hermes·저장은 펼치지 않은 것을 다룬다. `Case.steps` 는 펼친 것, `Case.own_steps` 는 스크립트 자기 단계다.
- **카드끼리:** 카드도 `uses` 를 쓴다. 바깥 카드의 입력은 `with: {title: "{{input.title}}"}` 처럼 안쪽 카드로 넘긴다. 카드는 매번 원본에서 다시 펼쳐 순환을 놓치지 않는다.
- **검증 오류:** 없는 카드, setup 이 아닌 카드, 카드에 없는 입력칸, 필수 입력 누락, 순환, 입력칸 없는 스크립트의 `{{input.x}}`, 파일에 직접 적은 `given`, 전제 단계까지 봐도 save 에 없는 outputs. 로드 때 틀린 스크립트는 빠지고 오류 목록에 남는다. 폼·Hermes·채팅 도구의 저장 검사도 지금 스크립트 목록으로 펼쳐 본다(`library`).
- **스냅샷:** 실행 기록에는 `Case.run_yaml()` 이 남는다. 펼친 단계 전체와 `given_by`(쓴 카드와 입력)가 들어가고 `uses` 는 없어 다시 읽어도 또 펼치지 않는다. 해시도 펼친 모양으로 계산해 카드가 바뀌면 스크립트 버전이 바뀐다.
- **판정:** 전제 단계가 틀리면 `fail` 이 아니라 `error` 이고 오류는 "전제 준비 실패(카드 id): …" 다. 테스트 계정·픽스처가 없어 건너뛴 것은 그대로 `skipped`.
- **커버리지:** 카탈로그 대조(`audit`)와 API 별 호출 목록(`scripts_by_op`)은 전제 단계를 보지 않는다. 단계 번호도 스크립트 자기 단계 기준이다.
- **화면:** 실행 결과에서 전제 단계는 "테스트 데이터 만들기 카드" 한 줄로 접히고 실패하면 펼쳐진다. 스크립트 화면 기본 정보에 테스트 데이터 만들기 카드 링크와 단계 수, 준비 작업 화면 단계 목록에 "테스트 데이터 만들기 카드 id" 표시가 붙는다.
- **폼:** 기본 정보에 "테스트 데이터 만들기 카드" 드롭다운과 카드 입력칸 표가 생긴다. 카드의 결과값이 변수 자동완성(`{{roomId}}`)과 setup 카드의 outputs 선택지에 뜬다. `/api/editor/context` 가 `setups` 를 준다. `editor.js` v5.
- **시드:** `setup.room-with-application` 은 `setup.room-open` 을, `setup.room-confirmed` 는 `setup.room-with-application` 을, `setup.room-ready-to-start` 는 `setup.room-confirmed` 를 쓴다. 룸 생성 요청 본문은 `setup.room-open` 한 곳에만 남았다. `room.apply-and-withdraw` 는 `uses: setup.room-open` 으로 줄였고 룸 생성 단계의 `op.createRoom:200` covers 가 빠졌다(`room.create-and-cancel` 이 확인한다).
- 테스트 152건 통과. 로컬 브라우저로 스크립트 화면, 폼(테스트 데이터 만들기 카드·입력칸·자동완성·검사), 준비 작업 화면을 확인했다. dev 실제 실행은 배포 뒤에 본다.

- **화면:** 대시보드 아래와 `/features` 에 기능·시나리오·케이스 트리(합계, 막대, 펼치기). 기능 화면 `/features/<기능>` 은 PRD 단계와 게이트, 케이스 표, 아직 테스트가 없는 거절 조건, 검증 결과. 케이스 화면 `/features/<기능>/<Sn>/<key>` 는 분기·거절이 일어나는 단계 문장, 전제, 기대 결과, 확인할 테스트 조건, 구현한 스크립트, 실행 이력, [스크립트 만들기 (폼)](케이스·제목·테스트 조건·계정·근거를 채워 연다). 스크립트 목록은 케이스 순서로 먼저, "시나리오에 연결되지 않은 스크립트"를 뒤에 모은다. 테스트 조건 상세에 "이 테스트 조건을 확인하는 케이스". nav 에 "시나리오".
- **파일 둘:** 룸 생성(S1 케이스 5, S2 케이스 4), 룸 참여 및 참여자 관리(S1 케이스 4). 케이스는 지금 스크립트가 있는 것과 PRD 분기, 예시 거절 하나(headcount-range)만 적었다. 나머지 거절 케이스는 6단계 Hermes 로 채운다. 지금 아직 테스트가 없는 거절 조건은 룸 생성 16개, 룸 참여 23개다.
- **§13 옮기기:** `room.create-and-cancel` 을 `room.create`(S1/happy), `room.cancel`(S2/cancel, `uses: setup.room-open`), `room.cancel-not-recruiting`(S2/room-recruiting) 셋으로 나눴다. 재취소는 `G.room.cancel#room-recruiting`(E1410)으로, 취소 성공은 `C.room.cancel` 로 covers 를 바로잡았다. `room.creation-limit` 은 S1/creation-limit, `room.apply-and-withdraw` 는 S1/withdraw 다.
- 두 파일은 지금 위키와 테스트 조건 목록에 대조해 오류·경고가 없다. 테스트 162건 통과. 로컬 브라우저로 트리, 기능 화면, 케이스 화면, 스크립트 목록, 테스트 조건 상세, 케이스에서 연 폼을 확인했다.

### 17.6 5단계 — 시나리오 폼 (2026-09-24)

- **변경 하나를 최신 파일에 적용한다.** 폼이 보내는 것은 파일 전체가 아니라 변경 하나(`op`)다. `scenarios.apply_op` 가 main 의 지금 파일에 그것을 다시 적용한다. 그래서 폼을 연 사이 다른 사람이 다른 케이스를 고쳐도 그 변경은 사라지지 않는다. 변경 종류는 넷이다. 케이스 넣기·고치기(`variant`), 케이스 지우기(`variant-delete`), 시나리오의 기본 테스트 계정·gates 고치기(`scenario`), 시나리오 지우기(`scenario-delete`). 파일이 없는 기능은 첫 케이스를 넣을 때 파일을 만든다.
- **검증으로 막기:** `App.scenario_check` 가 변경을 적용한 판으로 §6.1 을 돌려 오류가 있으면 저장하지 않고 폼에 오류를 보인다. 경고는 변경 기록에 남는다. 시나리오 자체는 PRD 2장이 정하므로 PRD 에 없는 시나리오는 폼으로 만들지 않는다. 케이스 key `new`·`edit`·`delete` 는 화면 주소와 겹쳐 쓰지 않는다. 고칠 때 key 는 바꿀 수 없다.
- **저장:** `App.save_scenario` 가 변경 기록(kind `scenario`·`scenario-delete`, 대상은 케이스 id 또는 `기능/Sn`)을 남기고 `qa-platform/scenarios/<기능>.yaml` 에 바로 커밋한다. 감사 로그는 `scenario.save`·`scenario.delete`. 폼으로 저장하면 `written_by` 는 떨어진다.
- **지우기:** 확인 창에 그 케이스·시나리오를 구현하던 스크립트를 보인다. 지우면 그 스크립트는 지우지 않고 `variant:` 만 뗀다(kind `case-unlink`, `reviewed` 는 그대로). 스크립트는 "시나리오에 연결되지 않은 스크립트"로 간다.
- **화면:** 기능 화면 시나리오마다 [+ 케이스], [시나리오 고치기], 시나리오 지우기. 아직 테스트가 없는 거절 조건 줄마다 [케이스로 추가] 가 종류·단계·key·제목·테스트 조건·확인 방식을 채워 폼을 연다. 같은 검사 key 가 게이트 둘에 있으면(host-only) 게이트 이름을 앞에 붙인다. 케이스 화면에 [폼으로 고치기] 와 지우기. 시나리오 폼은 PRD 단계마다 게이트 칸(자동완성)이다.
- **파일 모양:** 저장기는 손으로 쓴 파일과 같은 모양(두 칸 들여쓰기, 짧은 목록은 한 줄)으로 쓴다. 시드 두 파일도 이 모양으로 맞췄다. 달라진 것은 `:` 가 든 테스트 조건 id 에 붙는 따옴표뿐이다.
- 테스트 170건 통과. 로컬 브라우저로 [케이스로 추가] 에서 연 폼, 틀린 테스트 조건으로 저장했을 때 막히는 것, 시나리오 폼, 케이스 고치기 폼을 확인했다. 로컬에는 쓰기 토큰이 없어 실제 커밋은 테스트(가짜 GitHub)로만 확인했다.

### 17.7 6단계 — Hermes 로 케이스 채우기, 케이스에서 스크립트 만들기 (2026-09-24)

- **케이스 채우기 (`qa/scenario_ai.py`, 작업 kind `scenario`):** 기능 화면의 [Hermes 로 케이스 채우기]. 근거는 PRD 2장 원문, 단계와 요구 id, 그 기능의 게이트·검사(ref·message·ErrorCode·note·자동화 제외), 명령과 묶인 API(method·path), 지금 시나리오 파일, 아직 테스트가 없는 거절 조건이다. 기능의 게이트는 출처가 그 PRD 인 게이트와 명령, 명령의 게이트, 파일에 이미 적힌 게이트다.
- **합친다:** Hermes 가 낸 파일을 그대로 쓰지 않는다. 변경 종류 `merge` 로 이미 있는 케이스·이미 적힌 단계의 gates·actor 는 그대로 두고, 새 key 의 케이스와 비어 있던 단계의 gates 만 더한다. 사람이 쓴 것을 덮어쓰지 않으려는 것이다. 더한 케이스에는 `written_by: hermes` 가 붙고 케이스 화면에 "Hermes 작성" 이 뜬다. 폼으로 한 번 저장하면 떨어진다.
- **검증:** 합친 판으로 §6.1 을 돌린다. 막히면 오류와 앞 출력을 붙여 한 번 더 묻고, 그래도 막히면 저장하지 않고 작업이 실패로 끝난다(감사 로그 `hermes.rejected_by_validation`). 새로 더할 것이 없으면 커밋하지 않는다. 저장은 5단계와 같은 변경 기록·커밋 길이다(source `hermes-scenario`, 프롬프트 해시).
- **케이스에서 스크립트 (`App.job_variant_script`):** 케이스 화면의 [Hermes 로 스크립트 만들기]. 기존 스크립트 생성에 케이스의 종류·제목·분기·거절이 일어나는 단계 문장·전제·기대 결과·기본 계정과 테스트 데이터 만들기 카드 목록(id·입력·결과값)을 더한다. 스크립트 생성 규칙에 "준비 단계는 테스트 데이터 만들기 카드를 uses 로 받는다" 를 더했다. 나온 스크립트의 `variant:` 는 플랫폼이 박는다. 요청 테스트 조건은 케이스 checks 에 그 검사에 묶인 API 계약 테스트 조건(거절이면 같은 코드, 성공이면 2xx)을 더한 것이다. checks 가 없는 케이스는 근거가 없어 막는다.
- 테스트 176건 통과(가짜 Hermes·가짜 GitHub). 로컬에는 Hermes 가 없어 실제 모델 호출은 배포 뒤에 본다.
