# QA 플랫폼 — 사용자 시나리오로 테스트 관리하기 (설계)

> 상태: **설계 2판 (2026-09-24), 검토 중.** 1판 검토 답을 반영했다(§16). 남은 질문은 §15.
> 사용자 요청: "스크립트 기반은 너무 비직관적이다. 단일 정책은 결국 유즈케이스 안의 여러 로직 중 하나다. 시나리오는 AI 가 만들고, 사람이 CRUD 를 직접 다 할 수 있게 하자."
> 관련: [qa-platform-tc.md](qa-platform-tc.md)(TC 카탈로그), [qa-platform-editor.md](qa-platform-editor.md)(폼 편집, 이번에 저장 흐름이 바뀐다), [qa-platform-progress.md](qa-platform-progress.md)(Hermes 작업 SSE), [policy-ssot-split.md](policy-ssot-split.md)(PRD 요구 id, 게이트 검사 key).

## 1. 왜

- 지금 관리 단위는 **스크립트**다. 무엇을 한 스크립트에 묶을지는 쓴 사람 마음이다. `room.create-and-cancel` 은 이름 하나에 정상 생성, 취소, 재취소 거절이 섞여 있어 이름만 보고는 무엇을 확인하는지 알 수 없다.
- 정책 하나는 혼자 서 있지 않다. "최소 인원 미달이면 확정 거절" 은 룸 생성, 신청, 수락, 확정이 이어져야 드러난다. 정책은 유즈케이스 흐름 안의 한 분기다.
- 토스 QA 사례처럼 **사용자 흐름 하나를 두고 분기점마다 변형을 나열**하면 사람이 기능을 이해하는 방식과 같아진다. 실행도 "어느 변형을 돌릴까" 로 고르게 된다.
- 재료는 이미 있다. PRD 11개 모두 2장에 `### 시나리오 S1` 이 있고 규칙 줄마다 요구 id `R{n}` 가 있다. 규칙표 게이트 검사 194개에는 key 가 있고, 그중 93개에는 백엔드 ErrorCode 가 적혀 있다.

## 2. 구조 — 다섯 층

| 층 | 무엇 | 원본 | 예 |
|---|---|---|---|
| **기능** | PRD 문서 하나 | 위키 `raw/product/<PRD>.md` | 룸 생성 |
| **시나리오** | 행위자 하나가 목표 하나를 이루는 흐름 | **PRD 2장 `시나리오 Sn`**. QA 는 1:1 로 따른다 | S3 방장이 모집 중인 룸을 고치거나 취소한다 |
| **변형** | 흐름의 한 갈래 | 정상 흐름, PRD 분기, 규칙표 거절 규칙, 사람이 더한 것 | 최대 인원이 최소 인원보다 작으면 E1402 |
| **단계** | API 호출 하나 | 스크립트의 steps (지금과 같다) | POST /v1/rooms |
| **확인 항목** | TC | 지금의 TC 카탈로그 (지금과 같다) | `G.room.create#headcount-range` |

- **시나리오는 PRD 가 정한다.** QA 는 PRD 시나리오를 나누거나 합치지 않는다. 그래서 "QA 시나리오 몇 번이 PRD 어디까지인가" 를 잇는 칸이 없다. 시나리오가 모자라면 PRD 를 고친다(§3).
- **QA 가 더하는 것은 변형이다.** 변형 목록과 변형을 구현하는 스크립트가 QA 몫이다.
- **스크립트는 변형 하나를 구현한다.** 스크립트에 `variant:` 칸이 생긴다.
- 실행기의 단계 실행, TC 카탈로그, 실행 기록은 바뀌지 않는다. 실행기에는 전제 재사용(§8)만 더해진다.

### 2.1 변형의 종류

| kind | 화면 이름 | 어디서 나오나 |
|---|---|---|
| `happy` | 정상 흐름 | 시나리오마다 하나 이상 |
| `branch` | 분기 | PRD 2장의 `분기:` 줄 |
| `reject` | 거절 | 규칙표 게이트 검사 하나. 예: `G.room.create#headcount-range` |
| `extra` | 추가 | 사람이 더한 경계값, 회귀 사례 |

- 거절 변형은 **검사 하나에 변형 하나**가 기본이다. `headcount-range` 처럼 한 검사가 규칙 셋을 품으면 변형을 셋으로 나눌 수 있다.
- 변형마다 **확인 방식**이 있다. `auto` 는 스크립트로 확인하고, `manual` 은 사람이 확인한다.

### 2.2 테스트 없는 거절 규칙

1판에서 "거절 변형 후보" 라고 부른 것이다. 이름이 모호해서 바꾼다.

- 규칙표에는 기능마다 "이러면 거절한다" 는 규칙이 적혀 있다. 룸 생성에는 17개가 있고, 그중 하나가 "최대 인원이 최소 인원보다 작으면 E1402" 다.
- 이 규칙마다 거절 변형이 하나씩 있어야 빠짐없이 테스트한 것이다.
- **테스트 없는 거절 규칙**은 시나리오 단계에 걸린 게이트의 검사 중 아직 어느 변형도 확인하지 않는 것이다. 자동화 제외 목록에 있는 것은 뺀다.
- 플랫폼이 AI 없이 계산한다. 시나리오 화면에 "테스트 없는 거절 규칙 N개" 로 뜨고, 줄마다 [변형으로 추가] 버튼이 폼을 미리 채워 연다.
- 규칙 수가 곧 할 일의 크기다.

| 기능 | 게이트 검사 | ErrorCode 있음 |
|---|---|---|
| 룸 생성 | 22 | 17 |
| 룸 탐색 | 11 | 0 |
| 룸 참여 및 참여자 관리 | 29 | 20 |
| 룸 진행 확정 | 7 | 4 |
| 룸 진행 준비 | 27 | 20 |
| 룸 진행 | 31 | 6 |
| 룸 진행 마무리 및 출석 | 12 | 3 |
| 룸 방명록 | 8 | 3 |
| 유저 후기 및 신뢰 관리 | 18 | 8 |
| 회원 및 프로필 | 29 | 12 |
| 운영자 관리 | 규칙표 조각 없음 | |

- ErrorCode 가 없는 101개 중 24개는 `catalog/bindings.yaml` 에 ErrorCode 를 채워 두었다. 나머지 77개는 화면에서만 막는지, 백엔드가 E400 으로 막는지, 아예 안 막는지 문서로는 모른다. 이것을 어떻게 보일지는 §15 질문 1.

## 3. PRD 2장 구체화 (위키 작업)

지금 PRD 는 모두 `시나리오 S1` 하나뿐이다. 한 시나리오에 행위자와 목표가 여럿 섞여 있고, 4장에 있는 기능 상당수가 2장에 아예 없다. 예를 들어 회원 PRD 의 S1 은 가입만 다루고 이력서 보관, 프로필 수정, 탈퇴는 빠져 있다.

### 3.1 규칙

- **시나리오 하나 = 행위자 하나 + 목표 하나.** 행위자나 목표가 바뀌면 새 시나리오다.
- **4장의 기능 절은 어느 시나리오의 단계에서든 한 번은 나와야 한다.** 엣지 케이스 절과 알림 절은 빼도 된다.
- **새 내용을 지어내지 않는다.** 단계 문장은 3장, 4장에 이미 있는 규칙을 사용자 흐름으로 옮긴 것이다. 어긋나는 게 보이면 고치지 않고 `> ❓` 로 표시한다.
- **기존 줄은 그대로 둔다.** 이미 있는 `R1`~`Rn` 줄은 문장을 바꾸지 않고 알맞은 시나리오로 옮긴다. 문장을 바꾸면 그 요구를 인용한 SSOT 레코드에 드리프트 알림이 뜨기 때문이다.
- **새 줄에는 새 요구 id 를 붙인다.** 머리말 `next_req` 에서 번호를 받고 재사용하지 않는다.
- 이 규칙은 team-wiki-v2 `AGENTS.md` 의 PRD 절에 더한다. 편집은 에이전트가 한다.

### 3.2 나누기 제안

이 목록이 초안이다. 실제 단계 문장은 작업할 때 4장에서 옮긴다.

| 기능 | 시나리오 |
|---|---|
| 룸 생성 | S1 방장이 룸을 만든다 · S2 일정 여러 개로 룸을 한꺼번에 만든다 · S3 방장이 모집 중인 룸을 고치거나 취소한다 |
| 룸 탐색 | S1 조건으로 룸을 찾는다 · S2 내 면접을 모아 본다 |
| 룸 참여 및 참여자 관리 | S1 참가를 신청하고 결과를 기다린다 (철회, 재신청 포함) · S2 방장이 신청을 보고 수락하거나 반려한다 · S3 확정 전에 참여를 취소하거나 방장이 내보낸다 |
| 룸 진행 확정 | S1 방장이 진행을 확정한다 · S2 확정 뒤 일정을 바꾼다 |
| 룸 진행 준비 | S1 확정 참여자가 질문을 남긴다 · S2 남긴 질문과 꼬리질문을 지운다 |
| 룸 진행 | S1 방장이 진행을 시작하고 라운드를 연다 · S2 참여자가 질문하고 기록한다 · S3 라운드 피드백을 남긴다 |
| 룸 진행 마무리 및 출석 | S1 진행 시작 때 출석을 기록한다 · S2 클로징을 제출하고 룸이 끝난다 · S3 출석 기록을 정정한다 |
| 룸 방명록 | S1 참여자가 방명록에 글을 남긴다 · S2 나가거나 룸이 끝나면 방명록 접근이 바뀐다 |
| 유저 후기 및 신뢰 관리 | S1 클로징 뒤 후기를 남기거나 고친다 · S2 다른 회원의 신뢰 정보를 본다 · S3 받은 후기를 보고 신고한다 |
| 회원 및 프로필 | S1 가입하고 하던 흐름으로 돌아간다 · S2 프로필과 닉네임을 고친다 · S3 이력서를 보관하고 기본 이력서를 정한다 · S4 로그아웃하거나 탈퇴한다 |
| 운영자 관리 | S1 기준 데이터와 추가 요청을 처리한다 · S2 신고를 검토하고 조치한다 |

- 모두 29개다. 기능당 2~4개다.
- 시스템이 혼자 하는 전이는 시나리오 단계에 적되, 규칙표에서 `actor: system` 인 것은 자동화 제외 목록이 이미 빼 준다. 방명록 읽기 전용 전환, 미시작 룸 자동 취소가 여기에 해당한다.

### 3.3 절차

1. 에이전트가 위키 worktree 에서 PRD 11개의 2장을 고친다. AGENTS.md 규칙도 같은 커밋에 넣는다.
2. 정책 렌더러와 드리프트 검사를 로컬에서 돌려, 기존 요구의 문장이 바뀌지 않았는지 확인한다. 바뀐 요구가 0개여야 한다.
3. 변경 요약을 사용자에게 보여 주고 확인을 받은 뒤 위키 main 에 반영한다.

## 4. 어디에 두나 (확정)

**이 레포 `qa-platform/scenarios/<기능>.yaml`.**

- 시나리오 파일은 PRD 시나리오를 **인용**하고 변형을 **더한다**. 기획 원본이 아니라 테스트 설계다.
- 스크립트(`cases/`)와 같은 곳이라 저장 흐름(§9), 이미지에 굽기, 시작할 때 sync 를 그대로 쓴다.
- 파일 이름은 위키 조각 `기능/<PRD>.yaml` 과 같게 한다.

## 5. 파일 형식

```yaml
# qa-platform/scenarios/룸-생성.yaml
feature: 룸 생성                  # PRD 문서 이름
scenarios:
  - id: S1                        # PRD 2장 시나리오 번호와 같다. 제목과 단계는 PRD 에서 읽는다
    actor: qa-host                # 기본 테스트 계정
    gates:                        # 단계 요구 id 에 걸리는 게이트. 테스트 없는 거절 규칙이 여기서 나온다
      R6: [G.room.create]
    variants:
      - key: happy
        kind: happy
        title: 온라인 룸을 만들면 모집 중으로 열린다
        given: 활성 룸이 없는 방장
        then: 200, 상태 RECRUITING, 상세의 방장이 본인이다
        checks: [C.room.create, op.createRoom:200]
      - key: pasted-posting
        kind: branch
        at: R3
        title: 목록에 없는 공고는 링크를 붙여 그 자리에서 만든다
        mode: manual
      - key: headcount-range
        kind: reject
        at: R6
        title: 최대 인원이 최소 인원보다 작으면 E1402 로 거절된다
        given: minParticipants 4, maxParticipants 2
        then: 400 E1402, 룸이 만들어지지 않는다
        checks: [G.room.create#headcount-range]
    basis_hash: 3f9a1c            # 저장할 때 플랫폼이 계산. §10
```

- **시나리오 제목과 단계는 파일에 없다.** PRD 2장에서 읽어 화면에 보인다. 1판의 `steps` 칸은 PRD 가 구체화되면서 필요 없어졌다.
- **`at`:** 변형이 갈라지는 단계다. PRD 2장 단계의 요구 id 로 적는다.
- **`gates`:** 단계 요구 id 별로 걸리는 게이트다. Hermes 가 채우고 사람이 고친다.
- **전체 id:** `기능/시나리오/변형` 이다. 예: `룸-생성/S1/headcount-range`. 스크립트는 `variant: 룸-생성/S1/headcount-range` 로 가리킨다.
- **변형 key:** 거절 변형은 검사 key 를 그대로 쓴다. 한 시나리오 안에서 겹치면 게이트 이름을 앞에 붙인다. 예: `create.login-required`.
- **`checks`:** 이 변형이 확인해야 하는 TC 다. 스크립트의 covers 가 이것을 포함해야 한다.
- **상태는 저장하지 않는다.** 자동화됨, 사람이 확인, 제외, 테스트 없음은 스크립트와 제외 목록을 보고 매번 계산한다.

## 6. 누가 무엇을 채우나

| 일 | 누가 |
|---|---|
| 시나리오와 단계 | PRD (위키) |
| 단계에 걸리는 게이트 | Hermes 가 채우고 사람이 고친다. 게이트 68개 중 36개는 명령과 이름이 짝이라 결정론으로 먼저 제안한다 |
| **테스트 없는 거절 규칙** | **플랫폼이 계산** |
| 변형 제목, 전제, 기대 결과 | Hermes 가 채우고 사람이 고친다. 재료는 검사의 ref, message, error, note |
| 변형 상태 | **플랫폼이 계산** |
| 근거 변경 표시 | **플랫폼이 계산** |

### 6.1 결정론 검증

저장할 때마다 돈다. 폼으로 저장하든 Hermes 가 저장하든 같다. 오류는 저장을 막고, 경고는 보여만 준다.

- **오류:**
  - 시나리오 id 가 PRD 2장에 없다.
  - `at` 이나 `gates` 의 요구 id 가 그 시나리오의 단계에 없다.
  - 게이트나 checks 의 TC 가 없다. 옛 번호 id 는 별칭으로 풀어 받는다.
  - 변형 key 가 겹친다.
  - 스크립트의 `variant:` 가 없는 변형을 가리킨다.
- **경고:**
  - 거절 변형의 checks 가 `at` 단계의 gates 밖에 있다.
  - 한 변형이 검사 여러 개를 확인한다.
  - 한 변형을 스크립트 둘 이상이 구현한다.
  - 스크립트의 covers 가 변형의 checks 를 다 담지 않았다.

## 7. Hermes

모두 사람이 버튼을 눌러 시작한다. 기존 Hermes 작업 틀(`qa/jobs.py`)에서 돌아서 진행 카드와 SSE 가 그대로 붙는다.

- **[Hermes 로 변형 채우기]:** 기능 화면에 둔다. 작업 kind 는 `scenario` 다.
  - 입력은 PRD 2장 원문과 요구 id, 그 기능의 규칙표 조각(gates, commands, transitions), bindings, 제외 목록, OpenAPI 요약, 지금 시나리오 파일, 테스트 없는 거절 규칙이다.
  - 출력은 그 기능의 시나리오 파일 전체다.
  - §6.1 검증을 통과하면 **바로 저장**한다(§9). 실패하면 오류를 붙여 한 번 더 묻고, 그래도 실패하면 작업이 실패로 끝나고 저장하지 않는다.
- **[Hermes 로 다시 맞추기]:** 근거가 바뀐 시나리오(§10)에 둔다. 바뀐 문장과 지금 파일을 주고 고친 판을 받아 저장한다.
- **[Hermes 로 스크립트 만들기]:** 변형 화면에 둔다. 기존 스크립트 생성을 쓰되, 입력에 변형의 제목, 전제, 기대 결과, checks, 쓸 만한 전제 카드(§8)를 더한다. 결과 스크립트에는 `variant:` 가 채워진다.
- Hermes 가 저장한 항목에는 `written_by: hermes` 가 붙는다. 화면에 "Hermes 작성" 표시가 뜨고, 사람이 폼으로 한 번 저장하면 사라진다.

## 8. 전제 재사용 (`uses:`)

### 8.1 문제

"최소 인원 미달이면 진행 확정 거절" 을 확인하려면 룸 생성, 신청, 수락을 먼저 해야 한다. 지금은 스크립트마다 이 준비 단계 4~5개를 전부 적는다. 확정 기능의 거절 변형이 여럿이면 같은 준비 단계가 여러 스크립트에 복사된다. 요청 본문이 바뀌면 복사본을 전부 고쳐야 한다.

그 준비 과정은 이미 **테스트 데이터 만들기 카드**(suite `setup`)로 있다. `setup.room-open`, `setup.room-with-application`, `setup.room-confirmed` 같은 것들이다.

### 8.2 형식

```yaml
- id: room.confirm-under-min
  title: 최소 인원이 모이지 않으면 진행 확정이 E1431 로 거절된다
  suite: sanity
  variant: 룸-진행-확정/S1/min-participants
  actor: qa-host
  uses:
    setup: setup.room-with-application      # 이 카드의 단계를 먼저 돈다
    with: { title: "[QA] 확정 거절" }         # 카드 입력칸. 안 적으면 기본값
  steps:
    - name: 수락 없이 바로 확정
      covers: ["G.room.confirm#min-participants"]
      request: { method: POST, path: "/v1/rooms/{{roomId}}/confirmation" }   # roomId 는 카드의 outputs
      expect: { status: 409, error_code: E1431 }
    - name: 정리
      request: { method: POST, path: "/v1/rooms/{{roomId}}/cancellation" }
      expect: { status: 200 }
```

- 예시의 경로와 ErrorCode 는 설명용이다.
- `uses` 는 카드 하나만 받는다. 카드끼리도 `uses` 를 쓸 수 있다. 예를 들어 `setup.room-confirmed` 가 `setup.room-with-application` 을 쓰면 카드끼리의 중복도 사라진다. 순환은 검증에서 막는다.
- 카드의 `outputs` 가 스크립트의 변수가 된다. 위 예의 `{{roomId}}` 다.

### 8.3 실행

- **스크립트를 읽을 때 펼친다.** 로더가 카드의 단계를 입력값을 박은 채 스크립트 단계 앞에 붙이고, 각 단계에 `given: setup.room-with-application` 표시를 단다. 실행기의 단계 실행 코드는 그대로다.
- 실행 기록의 스냅샷에는 펼친 단계가 남는다. 나중에 카드가 바뀌어도 그때 무엇을 돌렸는지 보인다.
- **전제 단계가 실패하면 판정은 `error` 다.** 메시지는 "전제 준비 실패: 참가자가 신청 단계에서 409" 처럼 적는다. 확인하려던 규칙이 틀린 것(`fail`)과 구분하기 위해서다.
- 전제 단계는 covers 가 없으므로 TC 커버리지에 들어가지 않는다.
- 실행 결과 화면에서 전제 단계는 접어서 보인다.
- 폼의 기본 정보에 "전제 카드" 드롭다운과 입력칸이 생긴다. 고르면 카드의 outputs 가 변수 자동완성에 뜬다.

## 9. 저장 흐름 — 초안과 승인을 없앤다 (확정)

스크립트, 수동 작성 TC, 시나리오 모두 같다.

- **폼 저장:** §6.1 과 기존 스크립트 검증을 통과하면 바로 main 에 커밋되고 플랫폼에 반영된다.
- **Hermes 생성과 고치기:** 검증을 통과하면 바로 저장된다. "Hermes 작성" 표시가 붙는다.
- **삭제:** 확인 창 하나를 거쳐 바로 커밋한다. 시나리오나 변형을 지울 때는 그것을 가리키는 스크립트 목록을 확인 창에 보인다. 스크립트는 지우지 않고 "시나리오 밖" 으로 남긴다.
- **저장 전에 해 보기:** 폼에 [저장 전에 한 번 실행해 보기] 를 둔다. 지금 초안 시험 실행과 같은 기능이다.
- **되돌리기:** git 이력으로 한다. 스크립트와 시나리오 화면에 최근 커밋 몇 개를 링크로 보인다. 되돌리고 싶으면 그 판을 폼으로 열어 저장한다.
- **감사 로그:** `case.save`, `case.delete`, `scenario.save`, `scenario.delete`, `manual_tc.save`, `manual_tc.delete` 에 커밋 sha 를 남긴다. Hermes 저장은 누른 사람을 operator 로 남긴다.
- **초안 목록 화면(`/drafts`)은 없앤다.** 지금 남은 초안은 옮기는 날 한 번 목록으로 보여 주고 정리한다. drafts 테이블은 기록으로 남긴다.
- **토큰이 없는 환경:** 저장 대신 기존 [반영된 파일 받기] 로 끝난다.
- **실행은 여전히 사람이 시작한다.** Hermes 가 저장한 스크립트도 누군가 실행을 눌러야 돈다.

## 10. 드리프트 — 근거가 바뀌면

- 저장할 때 `basis_hash` 를 계산한다. 그 시나리오 PRD 단계 문장, `at` 과 `gates` 의 요구 문장, checks 검사 정의의 해시다.
- 지금 값과 다르면 시나리오와 변형에 **"근거가 바뀜"** 표시가 붙는다. 어느 요구 id 의 문장이 어떻게 바뀌었는지 전후를 보인다. [Hermes 로 다시 맞추기] 와 [폼으로 고치기] 가 옆에 있다.
- 검사나 요구 id 가 사라지면 **오류** 표시다.
- PRD 에 새 시나리오가 생기면 트리에 "변형 없음" 으로 나타난다. 새 검사가 생기면 테스트 없는 거절 규칙에 나타난다.
- 자동으로 고치지는 않는다.

## 11. 실행

- 트리에서 변형을 체크하고 [고른 변형 실행] 을 누른다. 기능이나 시나리오를 통째로 고를 수도 있다. 플랫폼은 변형을 구현한 스크립트 id 목록으로 바꿔 기존 `create_run` 을 부른다.
- 실행 결과와 위키 보고서는 기능, 시나리오, 변형 순서로 묶는다. 시나리오 밖 스크립트는 끝에 따로 둔다.
- 스위트 실행(smoke, sanity)은 그대로 둔다.

## 12. 화면

- **첫 화면:** 지금 대시보드를 그대로 두고 그 아래에 기능, 시나리오, 변형 트리를 붙인다 (확정).
  - 기능 줄마다 변형 수, 자동화됨, 사람이 확인, 제외, 테스트 없음, 테스트 없는 거절 규칙 수, 최근 결과를 막대로 보인다.
  - 펼치면 시나리오, 다시 펼치면 변형이 나온다. 변형 줄에 체크박스가 있어 바로 실행할 수 있다.
- **기능 화면 `/features/<기능>`:** 시나리오마다 PRD 단계가 요구 id 와 함께 나오고 변형 표가 이어진다. 그 아래 테스트 없는 거절 규칙과 [변형으로 추가] 가 있다. [Hermes 로 변형 채우기] 가 위에 있다.
- **변형 화면 `/features/<기능>/<시나리오>/<변형>`:** 근거 문장, 전제, 기대 결과, 확인할 TC, 구현한 스크립트, 실행 이력, 최근 커밋이 보인다. 버튼은 [폼으로 고치기], [스크립트 만들기 (폼)], [Hermes 로 스크립트 만들기] 다.
- **스크립트 목록**은 남긴다. 각 줄에 변형 이름이 붙고, `variant:` 없는 것은 "시나리오 밖" 으로 모인다.
- **TC 상세**에 "이 TC 를 확인하는 변형" 이 더해진다. **API 별로 모아 보기**도 그대로다.

## 14. 구현 순서

1. **저장 흐름 바꾸기:** 초안과 승인을 없애고 바로 저장한다. 이미 배포된 폼 편집에 먼저 적용한다.
2. **PRD 2장 구체화:** 위키 작업. §3.3 대로 사용자 확인을 받고 반영한다.
3. **전제 재사용:** `uses` 로더 펼치기, 검증, 판정, 폼 칸. setup 카드끼리의 중복도 줄인다.
4. **시나리오 읽기:** 파일 형식, 로더, §6.1 검증, 테스트 없는 거절 규칙 계산, 스크립트 `variant:`, 첫 화면 트리, 기능 화면, 변형 화면. 룸 생성과 룸 참여 두 기능 파일과 §13 옮기기도 여기에 넣는다.
5. **시나리오 폼:** 변형 만들기, 고치기, 지우기.
6. **Hermes:** 변형 채우기, 다시 맞추기, 변형에서 스크립트 만들기.
7. **실행과 드리프트:** 변형 골라 실행, 결과와 보고서 묶기, basis_hash 비교 표시.

단계마다 테스트를 더하고 커밋을 따로 한다. 2 는 위키 레포, 나머지는 이 레포다.
