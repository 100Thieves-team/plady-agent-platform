# QA 플랫폼 — 사용자 시나리오로 테스트 관리하기 (설계)

> 상태: **설계 1판 (2026-09-24), 검토 대기.** 사용자 요청: "스크립트 기반은 너무 비직관적이다. 단일 정책은 결국 유즈케이스 안의 여러 로직 중 하나다. 시나리오는 AI 가 만들고, 사람이 CRUD 를 직접 다 할 수 있게 하자."
> 관련: [qa-platform-tc.md](qa-platform-tc.md)(TC 카탈로그), [qa-platform-editor.md](qa-platform-editor.md)(폼·초안·main 커밋), [qa-platform-progress.md](qa-platform-progress.md)(Hermes 작업 SSE), [policy-ssot-split.md](policy-ssot-split.md)(PRD 요구 id·게이트 검사 key).

## 1. 왜

- 지금 관리 단위는 **스크립트**다. 무엇을 한 스크립트에 묶을지는 쓴 사람 마음이다. `room.create-and-cancel` 은 이름 하나에 정상 생성, 취소, 재취소 거절이 섞여 있다. 이름만 보고는 무엇을 확인하는지 알 수 없다.
- 정책 하나는 혼자 서 있지 않다. "최소 인원 미달이면 확정 거절" 은 룸 생성, 신청, 수락, 확정이 이어져야 드러난다. 정책은 유즈케이스 흐름 안의 한 분기다.
- 토스 QA 사례처럼 **사용자 흐름 하나를 두고, 분기점마다 변형을 나열**하면 사람이 기능을 이해하는 방식과 같아진다. 실행도 "어느 변형을 돌릴까" 로 고르게 된다.
- 재료는 이미 있다. 2026-09-23 작업으로 PRD 11개 모두 2장에 `### 시나리오 S1` 이 생겼고, 규칙 줄마다 요구 id `R{n}` 가 붙었다. 규칙표 게이트 검사 194개에는 key 가 있다. 이 중 93개는 오류 코드가 있어 API 로 거절을 확인할 수 있다.

## 2. 구조 — 다섯 층

| 층 | 무엇 | 원본 | 예 |
|---|---|---|---|
| **기능** | PRD 문서 하나 | 위키 `raw/product/<PRD>.md` | 룸 생성 |
| **시나리오** | 사용자 흐름 하나 | PRD 2장 `시나리오 S1` 을 따르는 플랫폼 파일 | 방장이 룸을 만든다 |
| **변형** | 흐름의 한 갈래 | 정상 흐름, PRD 분기, 규칙표 거절 조건 | 최대 인원이 최소 인원보다 작으면 E1402 |
| **단계** | API 호출 하나 | 스크립트의 steps (지금과 같다) | POST /v1/rooms |
| **확인 항목** | TC | 지금의 TC 카탈로그 (지금과 같다) | `G.room.create#headcount-range` |

- **스크립트는 변형 하나를 구현한다.** 스크립트에 `variant:` 칸 하나가 생긴다.
- 위 세 층(기능, 시나리오, 변형)은 **테스트 설계**다. 아래 두 층(단계, 확인 항목)은 **구현과 검증 기준**이다. 지금 플랫폼에는 아래 두 층만 있다. 이번 작업은 위 층을 더한다.
- 실행기, 단계 형식, TC 카탈로그, 실행 기록은 바뀌지 않는다.

### 2.1 변형의 종류

| kind | 화면 이름 | 어디서 나오나 | 개수 |
|---|---|---|---|
| `happy` | 정상 흐름 | 시나리오 하나에 보통 하나 | 시나리오 수만큼 |
| `branch` | 분기 | PRD 2장의 `분기:` 줄 | 지금 1개 (룸 생성 R3) |
| `reject` | 거절 | 단계에 걸린 게이트의 검사 하나 | 최대 194개, 오류 코드 있는 것 93개 |
| `extra` | 추가 | 사람이 더한 경계값, 회귀 사례 | 제한 없음 |

- 거절 변형은 **검사 하나에 변형 하나**가 기본이다. `headcount-range` 처럼 한 검사가 규칙 셋을 품으면 사람이 변형을 셋으로 나눌 수 있다. 한 변형이 검사 여러 개를 확인하는 것은 막지 않지만 경고한다.
- 변형마다 **자동화 방식**이 있다. `auto` 는 스크립트로 확인하고, `manual` 은 사람이 확인한다. 오류 코드가 없는 검사(화면 안내만 있는 것)는 `manual` 로 시작하길 권한다.

### 2.2 규모 (2026-09-24 위키 main 기준)

| 기능 | PRD 2장 단계 | 게이트 검사 | 오류 코드 있는 검사 |
|---|---|---|---|
| 룸 생성 | 6 (분기 1) | 22 | 17 |
| 룸 탐색 | 5 | 11 | 0 |
| 룸 참여 및 참여자 관리 | 10 | 29 | 20 |
| 룸 진행 확정 | 5 | 7 | 4 |
| 룸 진행 준비 | 5 | 27 | 20 |
| 룸 진행 | 9 | 31 | 6 |
| 룸 진행 마무리 및 출석 | 5 | 12 | 3 |
| 룸 방명록 | 5 | 8 | 3 |
| 유저 후기 및 신뢰 관리 | 3 | 18 | 8 |
| 회원 및 프로필 | 6 | 29 | 12 |
| 운영자 관리 | 7 | 규칙표 조각 없음 | |

- 자동화 제외 목록(`catalog/exclusions.yaml`)에 걸린 검사는 변형 후보에서 회색으로 빠진다. 운영자 전용과 OAuth 흐름이 여기에 해당한다.
- 지금 sanity 스크립트는 3개뿐이다. 트리가 생기면 "변형 100여 개 중 자동화 몇 개" 가 한눈에 보인다. 이 숫자가 앞으로 일의 목록이 된다.

## 3. 어디에 두나

**이 레포 `qa-platform/scenarios/<기능>.yaml` 에 둔다 (권장).**

- 시나리오와 변형은 **테스트 설계**다. 기획 원본이 아니다. 원본은 여전히 PRD 와 규칙표이고, 시나리오 파일은 요구 id 와 검사 key 로 그 원본을 **인용**만 한다. 고정 규칙 "TC 정본은 SSOT·PRD, 플랫폼은 파생만" 을 지킨다.
- 스크립트(`cases/`)와 같은 곳에 있어야 폼 편집, 초안, 승인 후 main 커밋 흐름을 그대로 쓴다. `Repo.replace_item`, `append_item`, 이미지에 굽기, 시작할 때 sync 가 모두 재사용된다.
- 파일 이름은 위키 조각 `기능/<PRD>.yaml` 과 같게 한다. 예: `scenarios/룸-생성.yaml`.
- 위키에 두는 안은 버렸다. 기획자가 PRD 를 고치면서 테스트 변형까지 맞춰야 하고, 플랫폼 폼에서 위키 레포로 커밋하는 길을 새로 열어야 한다.

## 4. 파일 형식

```yaml
# qa-platform/scenarios/룸-생성.yaml
feature: 룸 생성                  # PRD 문서 이름. 위키 기능/룸-생성.yaml 과 짝
scenarios:
  - id: S1
    title: 방장이 룸을 만든다
    prd: S1                       # 따르는 PRD 2장 시나리오. 플랫폼에서 나눈 시나리오면 같은 S1 을 여럿이 가리킨다
    actor: qa-host                # 기본 테스트 계정
    steps:                        # 사용자 흐름. 사람 말로 적는다. API 호출이 아니다
      - key: pick-posting
        text: 채용 공고와 직무·면접 단계를 고른다
        basis: [R2]
      - key: create
        text: 입력을 확인하고 룸을 만든다
        basis: [R6]
        gates: [G.room.create]    # 이 단계에서 걸리는 게이트. 거절 변형 후보가 여기서 나온다
    variants:
      - key: happy
        kind: happy
        title: 온라인 룸을 만들면 모집 중으로 열린다
        given: 활성 룸이 없는 방장
        then: 200, 상태 RECRUITING, 상세의 방장이 본인이다
        checks: [C.room.create, op.createRoom:200]
      - key: pasted-posting
        kind: branch
        title: 목록에 없는 공고는 링크를 붙여 그 자리에서 만든다
        at: pick-posting
        basis: [R3]
        mode: manual
      - key: headcount-range
        kind: reject
        at: create
        title: 최대 인원이 최소 인원보다 작으면 E1402 로 거절된다
        given: minParticipants 4, maxParticipants 2
        then: 400 E1402, 룸이 만들어지지 않는다
        checks: [G.room.create#headcount-range]
    reviewed: { on: 2026-09-24, by: 승인한 사람, basis_hash: 3f9a1c }
```

- **전체 id** 는 `기능/시나리오/변형` 이다. 예: `룸-생성/S1/headcount-range`. 스크립트는 `variant: 룸-생성/S1/headcount-range` 로 가리킨다.
- **변형 key:** 거절 변형은 검사 key 를 그대로 쓴다. 한 시나리오 안에서 key 가 겹치면(`login-required` 는 게이트 여러 곳에 있다) 게이트 이름을 앞에 붙인다. 예: `create.login-required`.
- **basis:** 요구 id 를 적는다. 다른 PRD 의 요구면 `룸 참여 및 참여자 관리 R41` 처럼 문서 이름을 붙인다.
- **checks:** 이 변형이 확인해야 하는 TC 다. 스크립트의 covers 가 이것을 포함해야 한다.
- **reviewed.basis_hash:** 승인할 때 플랫폼이 계산한 값이다. 인용한 요구 문장과 검사 정의의 해시다. §8 드리프트에 쓴다.
- **상태는 저장하지 않는다.** 자동화됨, 수동, 제외, 미작성은 스크립트와 제외 목록을 보고 매번 계산한다.

## 5. 뼈대는 결정론, 살은 AI 와 사람

AI 없이도 플랫폼이 계산할 수 있는 것은 모두 계산한다. Hermes 는 사람이 읽을 말과 묶음을 채운다.

| 일 | 누가 | 방법 |
|---|---|---|
| 시나리오 단계 목록 | Hermes 초안, 사람이 고침 | PRD 2장 번호 줄과 요구 id |
| 단계에 걸리는 게이트 | Hermes 초안, 사람이 고침 | 단계의 명령과 규칙표 게이트 이름. 게이트 68개 중 36개는 명령과 이름이 짝이라 바로 찾는다. 나머지는 조회 게이트다 |
| **거절 변형 후보** | **플랫폼** | 단계 `gates` 의 검사 중 아직 어느 변형의 checks 에도 없고 제외 목록에도 없는 것 |
| 변형 제목, 전제, 기대 결과 | Hermes 초안, 사람이 고침 | 검사의 ref, message, error, note |
| 변형 상태 | **플랫폼** | `variant:` 를 가진 승인된 스크립트, `mode`, 제외 목록 |
| 근거 변경 | **플랫폼** | basis_hash 와 지금 문장 비교 |

- 그래서 **Hermes 를 한 번도 부르지 않아도 트리는 쓸모가 있다.** 시나리오 화면에 "아직 변형이 없는 거절 조건 N개" 가 뜨고, 각 줄의 [변형으로 추가] 버튼이 폼을 미리 채워 연다.

### 5.1 결정론 검증

저장과 승인마다 돈다. 오류는 저장을 막고, 경고는 보여만 준다.

- **오류:**
  - basis 의 요구 id 가 PRD 에 없다.
  - gates 의 게이트나 checks 의 TC 가 없다. 옛 번호 id 는 별칭으로 풀어 받는다.
  - 변형 key 나 단계 key 가 겹친다.
  - `at` 이 없는 단계를 가리킨다.
  - 스크립트의 `variant:` 가 없는 변형을 가리킨다.
- **경고:**
  - 거절 변형의 checks 가 `at` 단계의 gates 밖에 있다.
  - 한 변형이 검사 여러 개를 확인한다.
  - 한 변형을 스크립트 둘 이상이 구현한다.
  - 변형이 요구한 checks 를 스크립트의 covers 가 다 담지 않았다.

## 6. Hermes 초안 — 기능 하나 단위

- 기능 화면의 [Hermes 로 시나리오 초안 만들기] 로 시작한다. 실행 시작은 사람이다. 작업은 기존 Hermes 작업 틀(`qa/jobs.py`)에 kind `scenario` 로 돌고, 진행 카드와 SSE 가 그대로 붙는다.
- **입력:** 플랫폼이 조립한다.
  - PRD 2장 원문과 요구 id
  - 그 기능의 규칙표 조각: gates 의 검사 key, ref, error, message, note, 그리고 commands, transitions
  - bindings(명령과 API), 제외 목록, OpenAPI 요약
  - 지금 시나리오 파일이 있으면 그 내용. 다시 맞추기일 때만 준다
  - §5 가 계산한 거절 변형 후보
- **출력:** 그 기능의 시나리오 파일 전체 YAML 이다. §5.1 검증을 통과해야 초안이 된다. 실패하면 오류를 붙여 한 번 다시 묻는다. 지금 스크립트 초안과 같은 방식이다.
- **다시 맞추기:** 근거가 바뀐 시나리오(§8)에서 [Hermes 로 다시 맞추기] 를 누르면, 지금 파일과 바뀐 문장을 주고 고친 판을 받는다. 초안 화면이 지금 파일과의 diff 를 보여 준다.
- **변형에서 스크립트로:** 변형 화면의 [Hermes 로 스크립트 초안] 은 기존 스크립트 초안 생성을 쓴다. 입력에 변형의 제목, 전제, 기대 결과, checks 가 더해지고, 결과 스크립트에 `variant:` 가 채워진다.

## 7. 사람이 CRUD — 폼

폼 편집(qa-platform-editor.md)과 같은 길을 탄다. 저장하면 초안이 되고, 승인하면 main 에 커밋되고, 플랫폼이 바로 다시 읽는다. 초안 kind 는 `scenario`, `scenario-delete` 가 더해진다.

- **시나리오 폼:** 제목, 따르는 PRD 시나리오, 기본 테스트 계정, 단계 카드.
  - 단계 카드에는 문장, 요구 id 고르기, 게이트 고르기가 있다.
  - 요구 id 칸은 PRD 2장 줄을 목록으로 보여 준다. 고르면 문장이 옆에 뜬다.
- **변형 폼:** 종류, 걸리는 단계, 제목, 전제, 기대 결과, 확인할 TC, 자동화 방식.
  - 거절 변형이면 검사를 고르는 칸이 먼저 나온다. 고른 검사의 ref, message, error 가 옆에 떠서 제목과 기대 결과를 쓰기 쉽다.
- **삭제:** 시나리오나 변형을 지우면, 그것을 가리키던 스크립트가 목록으로 뜬다. 스크립트는 지워지지 않는다. `variant:` 가 빈 "시나리오 밖 스크립트" 로 남는다.
- 편집 단위는 **시나리오 하나**다. 변형 하나를 고쳐도 그 시나리오 항목 전체를 바꾼다. 파일 구간 치환(`item_spans`)이 최상위 항목 단위이기 때문이다.
- 감사 로그: `scenario.form_save`, `scenario.delete_request`, 기존 `draft.approve`.

## 8. 드리프트 — 근거가 바뀌면

- 승인할 때 저장한 `basis_hash` 와 지금 PRD 문장, 검사 정의를 비교한다. 다르면 시나리오와 변형에 **"근거가 바뀜"** 표시가 붙는다. 어느 요구 id 의 문장이 어떻게 바뀌었는지 전후를 보여 준다.
- 검사가 규칙표에서 사라지면 그 변형은 **오류** 표시다. 요구 id 가 사라져도 같다.
- 새 검사가 생기면 §5 의 거절 변형 후보에 저절로 나타난다.
- 알림은 기존 위키 드리프트 알림에 한 줄을 더하는 정도로 둔다. 자동으로 고치지는 않는다.

## 9. 실행

- 트리에서 변형을 체크하고 [고른 변형 실행] 을 누른다. 기능이나 시나리오를 통째로 고를 수도 있다. 플랫폼은 고른 변형을 구현한 스크립트 id 목록으로 바꿔 기존 `create_run` 을 부른다. 실행 시작은 여전히 사람이다.
- 실행 결과 화면과 위키 보고서는 기능, 시나리오, 변형 순서로 묶어 보여 준다. 시나리오 밖 스크립트는 맨 끝에 따로 둔다.
- 스위트 실행(smoke, sanity)은 그대로 둔다.

## 10. 화면

- **`/scenarios` 시나리오 (새 첫 화면):** 기능 카드 목록이다. 카드마다 변형 수, 자동화됨, 수동, 제외, 미작성, 최근 실행 결과를 막대로 보인다.
- **`/scenarios/<기능>`:** 시나리오마다 단계가 PRD 문장, 요구 id 와 함께 나오고, 변형 표가 이어진다. 표의 칸은 종류, 제목, 상태, 스크립트, 최근 결과다. 그 아래 "아직 변형이 없는 거절 조건" 과 [변형으로 추가] 가 있다.
- **`/scenarios/<기능>/<시나리오>/<변형>`:** 근거 문장, 전제, 기대 결과, 확인할 TC, 구현한 스크립트, 실행 이력을 보여 준다. 버튼은 [폼으로 고치기], [스크립트 만들기 (폼)], [Hermes 로 스크립트 초안] 이다.
- **스크립트 목록**은 남긴다. 각 줄에 변형 이름이 붙고, `variant:` 없는 것은 "시나리오 밖" 으로 모인다.
- **TC 상세**에 "이 TC 를 확인하는 변형" 이 더해진다. **API 별로 모아 보기**도 그대로 남는다.

## 11. 지금 스크립트 옮기기

| 스크립트 | 옮길 곳 |
|---|---|
| `room.create-and-cancel` | 둘로 나눈다. 정상 생성은 `룸-생성/S1/happy` 로 간다. 재취소 거절은 룸 참여 기능의 취소 거절 변형으로 간다. 이때 covers 의 E1419 검사와 기대 E1410 이 어긋난 문제(policy-ssot-split.md §11)도 바로잡는다 |
| `room.apply-and-withdraw` | 룸 참여 기능의 "신청 후 철회" 정상 흐름 변형 |
| `room.creation-limit` | 룸 생성 S1 의 `extra` 변형 "중복 생성 제한 조회" |
| smoke 8개 (헬스, 카탈로그, 인증 오류 등) | 시나리오 밖에 둔다. API 점검이라 사용자 흐름이 아니다 |
| setup 7개 | 그대로 둔다. 테스트 데이터 만들기 카드다 |

- 옮기는 일은 첫 구현 커밋에 같이 넣는다. 시나리오 파일도 이때 룸 생성과 룸 참여 두 개만 손으로 쓴다. 나머지 기능은 Hermes 초안으로 채운다.

## 12. 구현 순서

1. **읽기:** 파일 형식, 로더, §5.1 검증, 거절 변형 후보 계산, 스크립트 `variant:`, 트리 화면 세 개 (읽기 전용). 두 기능 시나리오 파일과 §11 옮기기도 여기에 넣는다.
2. **폼:** 시나리오와 변형 폼, 초안 kind `scenario`·`scenario-delete`, 승인 후 커밋.
3. **Hermes:** 작업 kind `scenario`, 다시 맞추기, 변형에서 스크립트 초안.
4. **실행과 드리프트:** 변형 골라 실행, 결과와 보고서 묶기, basis_hash 비교 표시.

단계마다 테스트를 더하고 커밋을 따로 한다.

## 13. 하지 않는 것

- **여러 기능을 잇는 긴 흐름**(생성부터 마무리까지)은 이번에 두지 않는다. 시나리오는 기능 하나에 속한다. 다른 PRD 의 요구는 basis 로 인용만 한다.
- **전제 재사용:** setup 스크립트를 변형의 전제로 불러 쓰는 기능(`uses: setup.room-confirmed`)은 실행기를 바꾸는 일이라 이번 범위 밖이다. 확정, 진행 기능의 거절 변형을 자동화하려면 곧 필요해진다. §14 질문 5.
- 화면(브라우저) 테스트, 자동 실행, 자동 수정은 하지 않는다.
