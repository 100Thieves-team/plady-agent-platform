## 0. 한 줄 요약

플랫폼을 **세 가지 일** 중심으로 다시 짠다.

1. **Sanity 테스트**: 머지된 PR 하나를 고르고 버튼 하나를 누르면, Hermes 가 관련 스펙을 찾고, 모호한 곳을 알리고, 테스트 조건·케이스·스크립트를 만들거나 고치고, dev 에 실행해 결과를 낸다.
2. **QA 데이터**: 테스트용 룸·신청·계정을 만들고 지운다. 지금 기능을 더 쉽게 쓰게 한다.
3. **스모크 테스트**: 저장된 스크립트로 핵심 흐름 전체를 한 번에 돌린다.

화면은 **노트북 기준**(1440×800 안팎)으로 짠다. 왼쪽 메뉴의 주 메뉴는 네 개(홈 · Sanity · 스모크 · QA 데이터)로 줄이고, 나머지는 그 아래 "관리" 묶음으로 옮긴다.

## 1. 용어

처음 나오는 말만 풀어 둔다. 화면도 같은 말을 쓴다.

| 말 | 뜻 |
| --- | --- |
| Sanity 테스트 | 새로 바뀐 부분이 스펙대로 동작하는지 좁고 깊게 확인하는 테스트. 여기서는 **머지된 PR 하나**가 단위다 |
| 스모크 테스트 | 핵심 흐름 전체가 일단 돌아가는지 넓고 얕게 확인하는 테스트 |
| 스펙 | 위키의 PRD(기획 문서)와 규칙표(SSOT, 상태·게이트·명령). 테스트의 정답지다 |
| 테스트 조건 | 무엇을 확인해야 하는가. 규칙표·PRD·API 문서에서 나온다 |
| 케이스 | 시나리오 안의 한 갈래(정상 흐름 · 분기 · 거절 · 추가) |
| 스크립트 | 케이스를 dev 에 실제로 호출해 확인하는 YAML |
| 스펙 확인 필요 | Hermes 나 플랫폼이 스펙에서 모호한 곳, 또는 스펙과 코드가 다른 곳을 찾아 사람이 정해야 하는 상태 |

## 2. 지금 무엇이 불편한가

2026-09-27 로컬 화면을 직접 써 보고 정리했다.

- 메뉴가 13개다(대시보드, 실행 기록, 시나리오, 테스트 스크립트, 테스트 조건, 변경 기록, Hermes, API, API 호출, 테스트 데이터 만들기, 감사 로그, 가이드, 담당자). 무엇부터 해야 하는지 화면이 말해 주지 않는다.
- 대시보드 첫 화면에 표가 네 개 있다. 숫자는 많지만 "지금 내가 할 일" 이 없다.
- PR 을 검증하려면 사람이 여러 화면을 오가야 한다. dev 배포 목록 → 시나리오 → Hermes 케이스 채우기 → 케이스별 스크립트 만들기 → 실행 → 실패 분석. 각 단계가 따로 있고 이어 주는 흐름이 없다.
- 코드 id(`G.room.confirm#host-only`, `op.confirmRoom:E1410`)가 문장보다 앞에 나온다.
- 테스트 데이터 만들기 화면은 카드마다 설명·입력·Normal/Swagger·담당자·버튼이 한꺼번에 보여 길다.

## 3. 원칙

앞 설계의 원칙은 그대로 지킨다.

1. 실행 시작은 언제나 사람이다. PR 이 머지돼도 저절로 돌지 않는다. 플랫폼은 "검증 안 한 PR" 을 보여 주고 알림만 보낸다.
2. 모든 사람 행위는 감사 로그에 남는다.
3. 통과·실패 판정은 결정론 러너가 한다. Hermes 는 만들고, 고치고, 설명한다.
4. 스펙의 정본은 위키다. 플랫폼은 스펙을 고치지 않는다. 모호하거나 코드와 다르면 **질문을 만들어 사람에게 넘긴다.**
5. 검증 대상은 dev 다.

이번에 더하는 원칙:

6. **한 화면에는 한 가지 일.** 가장 중요한 버튼 하나만 파란색으로 크게 둔다.
7. **문장이 먼저, id 는 나중.** "방장만 진행을 확정할 수 있다" 를 먼저 쓰고 `G.room.confirm#host-only` 는 작게 뒤에 둔다.
8. **다음 할 일을 화면이 말한다.** 빈 화면, 기다리는 중, 실패 뒤에 무엇을 누르면 되는지 적는다.

## 4. 일 1 — Sanity 테스트 (PR 기준)

### 4.1 흐름

사람은 두 번만 누른다. PR 고르기, [Sanity 시작]. 그 뒤는 Hermes 와 플랫폼이 다섯 단계를 차례로 한다.

```text
[PR #138 고르기] → [Sanity 시작]  (사람)
  1. 관련 스펙 찾기     PR 변경 → API → 규칙표 → PRD 기능·시나리오
  2. 스펙 점검         모호한 곳 · 스펙과 코드가 다른 곳 · 없어진 API
        └ 사람이 정해야 할 것이 있으면 여기서 멈춘다 → [이대로 계속] 또는 [위키 고친 뒤 다시 점검]
  3. 테스트 조건·케이스 준비   새 스펙이면 채우고, 바뀐 스펙이면 다시 맞춘다
  4. 스크립트 만들기     자동으로 확인할 수 있는 케이스 중 스크립트가 없는 것
  5. 실행·검사         dev 에 실행 → 실패하면 Hermes 실패 분석
  → Sanity 결과  (PR 별로 남는다)
```

"실행 시작은 사람" 원칙과의 관계: [Sanity 시작]을 누른 사람이 다섯 단계 전체를 시작한 것으로 본다. 단계마다 담당자·시각·결과가 감사 로그에 남는다. 머지 이벤트로 저절로 시작하는 경로는 만들지 않는다.

### 4.2 단계별 내용

**1. 관련 스펙 찾기.** 플랫폼이 먼저 결정론으로 후보를 뽑고, Hermes 가 PR 본문·변경 요약을 읽고 고른다.

- PR 정보: GitHub 에서 제목·본문·변경 파일·커밋 메시지를 읽는다. 제목의 Linear 이슈 번호(MOI-541)도 쓴다.
- 결정론 후보: 변경된 컨트롤러의 경로 → API(operationId) → API 매핑 → 규칙표 명령·게이트 → 그 규칙의 출처 PRD 요구 id → 기능·시나리오. 도메인 폴더 이름(room, review …)도 후보에 넣는다.
- 백엔드의 결정 기록(`.worklog/*/decisions.md`)이 PR 에 있으면 근거로 함께 준다.
- Hermes 출력은 `{기능, 시나리오, 요구 id, 이유}` 목록이다. 플랫폼은 위키에 있는 기능·요구 id 만 받는다.

**2. 스펙 점검.** 두 가지를 합친다.

- 플랫폼 결정론 점검:
  - 스크립트나 API 매핑이 가리키는 API 가 dev API 문서에서 없어졌다.
  - 코드에는 있는데 API 문서에 없다(예: `PUT /v1/rooms/{roomId}`).
  - PRD·규칙표가 마지막 저장 뒤 바뀌었다(지금의 "PRD·규칙표 바뀜").
  - 규칙표에 없는 기능(예: 운영자 관리는 게이트·명령이 없다).
- Hermes 점검: PR 변경과 스펙 원문을 나란히 읽고 **모호한 곳**과 **스펙과 코드가 다른 곳**을 문장으로 낸다. 각 항목은 `{종류, 스펙 위치, 코드 위치, 무엇이 다른가, 사람에게 묻는 질문, 추천}` 이다.

찾은 것이 있으면 Sanity 는 **"스펙 확인 필요"** 로 멈춘다. 사람은 둘 중 하나를 누른다.

- [위키 고친 뒤 다시 점검]: 위키에서 PRD·규칙표를 고친 뒤 누른다. 2단계부터 다시 한다.
- [이대로 계속]: 사유를 적고 누른다. 모호한 항목에 걸린 케이스는 "사람이 확인" 으로 두고 나머지를 이어 간다.

질문 목록은 [Slack 으로 보내기] 버튼으로 기획 담당에게 넘길 수 있다(WIKI_SLACK_WEBHOOK_URL). 사람이 누를 때만 보낸다.

**3. 테스트 조건·케이스 준비.** 이미 있는 기능을 잇는다. 범위는 1단계에서 찾은 요구에 걸린 케이스와 그 시나리오의 정상 흐름이다. 시나리오 전체가 아니다(PR #138 이면 케이스 28개).

- 규칙표에서 나오는 테스트 조건은 위키가 바뀌면 저절로 바뀐다. 플랫폼은 무엇이 바뀌었는지 보여 준다.
- 규칙표로 적히지 않은 PRD 요구는 Hermes 가 "수동 작성 테스트 조건" 으로 제안해 저장한다(지금의 P4d).
- 시나리오 파일이 없거나 케이스가 빈 기능은 [Hermes 로 케이스 채우기]와 같은 방식으로 채운다.
- 지난 저장 뒤 바뀐 요구에 걸린 케이스는 [Hermes 로 다시 맞추기]와 같은 방식으로 고친다.
- API 가 없어진 케이스는 지우지 않는다. "스펙 확인 필요" 로 표시하고 2단계 질문에 묶는다.

**4. 스크립트 만들기.** 이번 범위의 케이스 중 자동으로 확인할 수 있는데 스크립트가 없는 것마다 Hermes 가 스크립트를 쓴다. 검증을 통과하면 바로 main 에 저장하고 "Hermes 작성" 표시를 단다(지금 규칙). 규칙표가 바뀌어 스크립트의 검증 항목이 낡았으면 [바뀐 테스트 조건에 맞게 스크립트 다시 쓰기](지금의 P4c)를 한다.

**5. 실행·검사.** 이번 범위의 스크립트를 dev 에 실행한다. 실행 종류는 `sanity`, PR 번호를 기록에 남긴다. 실패한 스크립트마다 Hermes 실패 분석(버그 · 스크립트 낡음 · 환경)을 붙인다.

### 4.3 Sanity 결과

PR 마다 한 장이 남는다. 맨 위에 한 문장으로 결론을 쓴다.

- 예: "스펙 확인이 2건 필요해요. 나머지 케이스 14개 중 13개가 통과했어요."
- 그 아래: 스펙 확인 필요 목록 → 바뀐 테스트 조건·케이스 → 새로 만든 스크립트 → 실행 결과(기능 · 시나리오 · 케이스로 묶어) → 실패 분석.
- [위키에 보고서 게시]는 지금처럼 사람이 누를 때만.

### 4.4 PR 목록

- GitHub 에서 dev 로 머지된 PR 을 읽는다(지금 "dev 배포" 목록의 출처와 같다).
- 상태: 검증 안 함 · 진행 중 · 스펙 확인 필요 · 통과 · 실패.
- 인프라·문서만 바꾼 PR(변경 파일이 `infra/`, `docs/`, `.github/` 뿐)은 "API 변경 없음" 으로 흐리게 두고 맨 뒤로 보낸다.

### 4.5 실제 예 — PR #138 (MOI-541)

오늘 이 설계를 쓰며 실제로 확인한 것이다. 2판이 있었다면 Sanity 가 찾았어야 할 항목이다.

| 종류 | 무엇 | 사람에게 묻는 것 |
| --- | --- | --- |
| 스펙과 코드가 다름 | 룸 취소 API(`POST /v1/rooms/{roomId}/cancellation`)가 지워졌다(DR-002). 방장이 나가면 위임하고, 후임이 없을 때만 취소된다. PRD 「룸 생성」 S2 `R147` 은 "모집 중인 룸을 취소한다" 가 그대로다 | PRD `R147` 을 백엔드처럼 "방장이 나가면 위임 또는 취소" 로 바꿀까요 |
| 스펙과 코드가 다름 | 진행 완료와 출석 기록이 나뉘었다(DR-003). 완료 뒤 방장이 출석을 한 번 기록한다. PRD 「룸 진행 마무리 및 출석」 S2 `R63` 은 "출석을 제출하면 완료된다" 다 | `R63` 을 "완료 뒤 출석 기록" 순서로 바꿀까요 |
| 모호함 | 확정 뒤 방장이 위임되면 모집 중으로 돌아가 다시 확정한다(DR-002). 「룸 진행 확정」에는 이 규칙이 없다 | 재확정 규칙을 규칙표에 넣을까요 |
| 코드에 있고 문서에 없음 | `PUT /v1/rooms/{roomId}`(룸 수정)가 컨트롤러에 있지만 dev API 문서에 없다 | REST Docs 에 추가를 요청할까요 |
| 영향 | 스크립트 `room.cancel`, `room.cancel-not-recruiting` 은 없는 API 를 부른다. 테스트 데이터 카드 "진행 시작 직전 상태의 룸" 은 MVP 에 진행 중 상태가 없어 쓸 곳이 없다 | 위 두 질문이 정해지면 Hermes 가 고친다 |

이번 작업에서 이미 고친 것: 정리 단계가 취소 API 를 쓰던 스크립트 3개를 dev QA 룸 삭제로 바꿨고, API 매핑에 진행 완료를 더했다(커밋 212bc36).

## 5. 일 2 — QA 데이터

지금 "테스트 데이터 만들기" 와 "QA 데이터 정리" 를 한 화면으로 합친다.

- 왼쪽 열: **만들기 목록**. 목적별로 묶는다.
  - 룸: 모집 중인 룸 · 신청이 들어온 룸 · 진행 확정된 룸 · 완료할 수 있는 룸
  - 계정·이력서: QA 회원 만들기 · 이력서 목록 보기 · 이력서 요약 완료
- 오른쪽 열: **지금 dev 에 남은 QA 데이터** 표(종류 · 이름 · 만든 때 · [지우기])와 [전부 지우기]. 전부 지우기는 가운데 확인 창에 목록을 보여 주고 확인을 받는다.
- 목록의 한 줄은 제목과 한 줄 설명만 보인다. 누르면 오른쪽에서 입력 패널이 열리고, 필요한 입력만 보인다. 기본값이 있으면 입력 없이 [만들기](⌘↵) 하나로 끝난다. 목록은 가려지지 않아 다른 카드로 바로 옮겨 갈 수 있다.
- 만든 뒤에는 같은 패널에 결과값(roomId 등)을 복사 버튼과 함께 보여 주고, [방금 만든 것 지우기]를 둔다.
- Normal · Swagger 보기는 패널 안의 "요청 원문 보기" 로 접어 둔다.

## 6. 일 3 — 스모크 테스트

- 왼쪽: 범위 표. **전체** · **기능별로 고르기** · **지난번 실패만** 중 하나를 고르고, 표에 기능별 스크립트 수·단계 수·지난 결과가 보인다.
- 오른쪽: 실행 패널. 고른 스크립트 수, 예상 시간, 실행 종류와 [스모크 실행]. 담당자 확인은 가운데 확인 창으로.
- 실행 중에는 진행 막대와 지금 도는 스크립트 이름을 보여 준다(지금의 SSE).
- 결과 첫 줄은 문장이다. "스크립트 16개 중 14개 통과, 2개 실패." 아래 표는 실패를 맨 위로 올리고, 실패 줄에 실패 이유와 Hermes 분석을 바로 적는다.
- 반복 실행(같은 스크립트를 n번 돌려 흔들림을 보는 것)은 아직 정하지 않았다(§10-5).

## 9. 데이터와 구현

### 9.1 새로 저장하는 것

- `sanity` 표: id, pr_number, pr_title, sha, status(queued · running · needs_spec · passed · failed · canceled), step(1~5), operator, created_at, finished_at, scope(JSON: 기능·시나리오·케이스), findings(JSON 목록), run_id, job_ids.

- Hermes 작업 진행 표시(SSE, `jobs`)를 Sanity 다섯 단계에 그대로 쓴다. 단계 하나가 작업 하나다.

- 새로 만드는 Hermes 일은 두 가지다. 관련 스펙 찾기, 스펙 점검.

### 9.3 구현 순서 (검토 뒤)

1. 화면 틀: 새 색·글꼴·버튼, 왼쪽 메뉴(주 메뉴 네 개와 관리 묶음), 홈. 기존 화면은 새 모양만 받는다.

3. 스모크 화면.
4. Sanity 1: PR 목록, 관련 스펙 찾기, 스펙 점검, 멈춤과 계속.
5. Sanity 2: 준비 · 스크립트 · 실행을 잇고 Sanity 결과 화면.
6. 관리 화면 정리, 도움말·가이드·문서.

단계마다 테스트를 더하고 배포 뒤 운영에서 확인한다.

### 12.1 설계에서 달라진 것

- Sanity 실행 기록의 실행 종류는 새로 만들지 않고 `deploy-sanity` 를 쓴다(화면 이름은 "Sanity"). 옛 배포 검증 실행도 같은 이름으로 보인다.

### 13.1 확인한 사실

- 요청은 브라우저가 아니라 **플랫폼 서버가** 보낸다. 운영 플랫폼(qa.agent.plady.io, EC2)에서 `localhost:8080` 을 부르면 노트북이 아니라 EC2 자기 자신을 부른다. 노트북의 로컬 서버를 쓰려면 둘 중 하나다.
  - 로컬 서버를 터널(cloudflared · ngrok)로 공개 주소를 받아 등록한다.
  - 플랫폼을 노트북에서 띄운다(`python3 qa-platform/app.py`). 이때는 `localhost` 를 그대로 쓸 수 있다.
- 테스트 계정 토큰은 대상의 `POST /v1/auth/dev-sessions` 로 받는다. local·dev 프로파일에서만 열린다. live 는 막혀 있다.
- 테스트 계정(qa-host · qa-guest)은 dev DB 의 회원 id 다. 다른 서버의 DB 에는 그 회원이 없을 수 있다.
- 지금 토큰 캐시는 계정 이름으로만 저장한다. 대상이 둘 이상이면 섞인다(고쳐야 한다).
- 실행 기록에는 이미 대상 주소(`runs.base_url`)가 남는다.

### 13.2 제안

- **대상 목록**: dev 는 기본으로 늘 있다. [+ 대상 추가]로 이름·주소를 등록한다. 목록은 모두가 함께 쓰고(DB), 등록·삭제는 감사 로그에 남는다.
- **고르는 곳**: 왼쪽 메뉴 위에 "대상" 선택 상자. 고른 대상은 담당자별로 기억한다. 실행·API 호출·QA 데이터·Sanity 가 모두 그 대상으로 간다. 확인 창과 실행 결과에 대상을 크게 적는다. dev 가 아니면 주황 띠로 표시한다.
- **막는 것**: live 주소(`api.moimyeon.plady.io`)는 등록을 거절한다(고정 규칙: 검증 대상은 dev, live 와 무관). 운영 플랫폼에서는 내부 주소(localhost · 사설 IP · 169.254 · 도커 서비스 이름)도 거절한다. 서버가 자기 내부를 부르게 되는 것을 막으려는 것이다. 노트북에서 띄운 플랫폼에서는 localhost 를 허용한다.
- **등록 때 확인**: 그 주소의 `/actuator/health` 와 `dev-sessions` 를 한 번 불러 보고 결과를 보여 준다.
- **테스트 계정**: 대상마다 회원 id 를 따로 적을 수 있게 한다. 비우면 dev 와 같은 id 를 쓴다. 없으면 QA 데이터 화면의 [QA 회원 만들기]로 그 대상에 만든다.
- **토큰 캐시**: (대상, 계정) 으로 나눈다.

### 13.3 결정과 구현 (2026-09-27)

사용자가 세 가지 모두 추천안을 골랐다. 로컬 서버는 터널 주소와 노트북 플랫폼 둘 다, 고른 대상은 담당자별로 전체에, 테스트 계정은 대상마다 따로.

- 저장: `targets` 표(이름·주소·테스트 계정·등록 때 확인 결과), 담당자별 선택은 `settings` 표 `target:<담당자>`. 서버에 두므로 뒤에서 도는 Sanity 작업도 같은 대상을 쓴다.
- `App.target_for(담당자)` 가 실행 만들기(`runs.base_url`, meta.target), QA 데이터, 테스트 계정 토큰에 쓰인다. 토큰 캐시는 (대상 주소, 계정)으로 나눴다.
- 화면: 왼쪽 메뉴 맨 위 "대상 서버" 선택 상자와 [+], 관리의 "대상 서버" 화면(`/targets`), dev 가 아니면 모든 화면 위 주황 띠.
- 노트북 플랫폼 판단: `QA_PUBLIC_URL` 이 localhost·127.0.0.1 이거나 `QA_ALLOW_LOCAL_TARGETS=1`.
- 남은 한계: 내부 주소 검사는 등록할 때 이름을 한 번 풀어 본다. 나중에 그 이름이 내부 주소로 바뀌는 경우는 막지 않는다.

## 14. 스펙 확인에서 위키 수정까지 (구현됨 2026-09-28)

사용자 결정(2026-09-28): [추천대로]를 누르면 PRD 가 고쳐질 거라 생각했다. §10-3("Sanity 는 질문만 만들고 위키는 사람이 고친다")을 바꾼다. **플랫폼이 수정안을 만들고, 사람이 확인하고 반영한다.**

### 14.1 확인한 사실 (2026-09-28, 운영 서버에서 dry run)

- PRD(`raw/product/*.md`)는 고칠 수 있는 raw 다(wiki.toml `revisable`). `wiki_apply` mode `archive` 로 쓴다. dry run 통과.
- 규칙표 조각(`wiki/policy/_src/**.yaml`)은 `wiki_apply` 가 거절한다("slug cannot have a file extension"). `wiki_content_write`(asset 경로 `policy/_src/...`) 뒤 `wiki_content_commit` 으로 쓴다. 플랫폼 토큰으로 두 도구가 보인다. 둘 다 레지스트리의 approve 등급이다. 여기서 승인은 사람이 [위키에 반영]을 누르는 것이고, 감사 로그에 남는다.
- 위키 규칙: PRD 를 고치면 같은 작업에서 규칙표도 맞춘다. 조립본 `상태-SSOT.yaml` 은 고치지 않는다(EC2 렌더러가 조각이 바뀌면 다시 조립한다). 위키 CI 가 PRD 요구 줄의 변경과 그 요구를 인용한 규칙표 기록을 알려 준다.

### 14.2 흐름

```text
스펙 확인 항목 [추천대로] 또는 [다르게]+어떻게
  → 결정 기록 (지금과 같음)
  → Hermes 작업 "수정안 만들기" (사람이 누른 것으로 시작)
      근거: 항목(스펙·코드·질문·추천·결정), 그 기능의 PRD 전문, 규칙표 조각(기능/<PRD>.yaml, 필요하면 상태·공통)
      출력: 고칠 곳 목록 [{path, find, replace}] 과 한 줄 요약
  → 플랫폼 검증
      find 가 파일에 정확히 한 번 있는가 · 고칠 수 있는 파일인가(scope 기능의 PRD, _src 조각. 조립본 금지)
      PRD 요구 id 를 지우지 않았는가 · 조각을 바꾼 결과가 조립 검사(ssot_load check)를 통과하는가
  → 화면: 항목 아래 "수정안" — 바뀐 줄 비교, [위키에 반영] [버리기] [다시 만들기]
[위키에 반영] (사람)
  → 수정안을 만든 뒤 위키 파일이 바뀌었으면 거절하고 [다시 만들기]를 권한다
  → PRD 는 wiki_apply(archive) 한 번, 조각은 content_write 뒤 content_commit 한 번
  → 감사 로그 sanity.spec.apply(파일·커밋), 항목에 "위키에 반영됨"
  → 이어서 2단계부터 다시 점검 (반영을 누른 것이 곧 다시 점검의 시작)
```

- 여러 항목의 수정안이 있으면 [수정안 n개 한 번에 반영]으로 커밋을 한 번에 묶는다.
- 수정안을 만들 수 없는 종류(없어진 API, API 문서 누락, 규칙표 없음)는 지금처럼 결정만 남긴다.
- 이미 [추천대로]로 정한 항목(PR #139 여섯 건)에는 [수정안 만들기] 버튼이 생긴다.
- 새 요구 문장이 필요하면 Hermes 는 그 PRD 에서 가장 큰 요구 id 다음 번호를 쓴다. 결정 근거로 `.worklog` 결정 id 와 PR 번호를 줄 끝 메모로 남기게 한다.

### 14.6 고친 것: 드리프트 경고와 수정안끼리 충돌 (2026-10-02)

운영에서 두 문제가 나왔다.

1. **반영하면 위키 CI 가 드리프트로 경고했다.** 위키 렌더러는 `index.yaml` 의 `meta.기준_문서[<PRD>]` 값이 바뀔 때만 sync-manifest 의 요구 문장 기준을 지금 PRD 로 옮긴다(render_wiki.py manifest). 수정안이 PRD 문장을 고치고 이 값을 안 올려서, CI(policy-drift-check)가 "문장이 바뀜" 으로 Slack 경고와 이슈를 냈다(a5c87c1, 위키 이슈 #2).
2. **같은 문서를 고친 수정안이 서로 막았다.** 찾아 바꾸기는 find 원문이 정확히 한 번 있어야 한다. Hermes 가 find 에 앞뒤 문맥을 넣으므로, 앞 수정안이 그 문맥을 바꾸면 같은 줄이 아니어도 뒤 수정안이 실패했다(예: 「룸 진행 확정」 R49). 사람은 [다시 만들기]를 눌러야 했다.

고친 내용.

- **기준 날짜.** 반영할 때 PRD 가 바뀌면 플랫폼이 `index.yaml` 의 그 문서 값을 반영 시각(KST, 분까지)으로 올려 같은 커밋 묶음에 넣는다. 이미 같은 값이면 초까지 적어 반드시 바뀌게 한다. Hermes 는 이 값을 고치지 않는다.
- **쓰는 순서.** 규칙표 조각 → PRD(`wiki_apply`) → `index.yaml` → `wiki_content_commit`. 렌더러는 조각 해시가 바뀔 때 디스크의 PRD 를 읽으므로, 기준 날짜는 PRD 를 쓴 뒤에 써야 새 문장이 기준이 된다.
- **위키 CI.** 커밋과 렌더 사이에 push 가 끼면 CI 가 렌더 전 상태를 본다. `check_policy_refs.py` 는 `index.yaml` 의 기준 값이 manifest 의 baseline 과 다른 문서를 "렌더 대기" 로 보고 문장 비교를 건너뛴다. 요구 id·절 검사는 그대로 한다(team-wiki-v2).
- **인용 기록.** 수정안을 만들 때 그 항목의 요구를 인용한 규칙표 기록(조각의 source `PRD/<문서> R<n>`)을 찾아 Hermes 에게 목록으로 주고, 그 기록이 있는 조각(`상태/*` 포함)도 고칠 수 있게 한다. 화면에는 PRD 문장이 바뀌는 요구마다 인용한 기록과 이번 수정안이 고친 기록을 보여 준다.
- **3-way merge.** 수정안을 만들 때 바뀐 파일의 원래 본문(base)과 고친 본문(after)을 `data/specfix/<sha>.txt` 에 저장한다. 반영할 때 지금 파일에 줄 단위 3-way merge 로 얹는다. 다른 줄이면 문맥이 바뀌어도 합친다. 같은 줄을 서로 다르게 고쳤을 때만 충돌이다. 저장본이 없는 옛 수정안은 찾아 바꾸기로 한다.
- **충돌하면 다시 만들기.** 여러 개를 반영할 때 충돌한 수정안은 빼고 나머지만 커밋한다. 충돌한 수정안은 플랫폼이 Hermes 에게 지금 위키 기준으로 다시 만들게 하고, 화면에 "다시 만들었어요, 확인 후 반영" 으로 보인다. 위키에는 사람이 다시 [위키에 반영]을 눌러야 쓴다. 감사 로그 `sanity.spec.conflict`.
- **남은 수정안 다시 계산.** 하나를 반영하면 같은 Sanity 의 대기 수정안은 지금 파일 기준으로 base·after·바뀐 줄을 다시 계산한다. 같은 줄이면 위처럼 다시 만든다.
- 시험: tests/test_specfix.py 7건(merge3, 기준 날짜, 인용 기록, 문맥이 겹친 두 수정안, 충돌 뒤 다시 만들기).
