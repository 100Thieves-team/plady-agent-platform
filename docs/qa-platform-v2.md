## 0. 한 줄 요약

플랫폼을 **세 가지 일** 중심으로 다시 짠다.

1. **Sanity 테스트**: 머지된 PR 하나를 고르고 버튼 하나를 누르면, Hermes 가 관련 스펙을 찾고, 모호한 곳을 알리고, 테스트 조건·케이스·스크립트를 만들거나 고치고, dev 에 실행해 결과를 낸다.
2. **QA 데이터**: 테스트용 룸·신청·계정을 만들고 지운다. 지금 기능을 더 쉽게 쓰게 한다.
3. **스모크 테스트**: 저장된 스크립트로 핵심 흐름 전체를 한 번에 돌린다.

화면은 **노트북 기준**(1440×800 안팎)으로 짠다. 왼쪽 메뉴의 주 메뉴는 네 개(홈 · Sanity · 스모크 · QA 데이터)로 줄이고, 나머지는 그 아래 "관리" 묶음으로 옮긴다.

## 1. 용어

처음 나오는 말만 풀어 둔다. 화면도 같은 말을 쓴다.

| 말 | 뜻 |
| --- | --- |
| Sanity 테스트 | 새로 바뀐 부분이 스펙대로 동작하는지 좁고 깊게 확인하는 테스트. 여기서는 **머지된 PR 하나**가 단위다 |
| 스모크 테스트 | 핵심 흐름 전체가 일단 돌아가는지 넓고 얕게 확인하는 테스트 |
| 스펙 | 위키의 PRD(기획 문서)와 규칙표(SSOT, 상태·게이트·명령). 테스트의 정답지다 |
| 테스트 조건 | 무엇을 확인해야 하는가. 규칙표·PRD·API 문서에서 나온다 |
| 케이스 | 시나리오 안의 한 갈래(정상 흐름 · 분기 · 거절 · 추가) |
| 스크립트 | 케이스를 dev 에 실제로 호출해 확인하는 YAML |
| 스펙 확인 필요 | Hermes 나 플랫폼이 스펙에서 모호한 곳, 또는 스펙과 코드가 다른 곳을 찾아 사람이 정해야 하는 상태 |

## 2. 지금 무엇이 불편한가

2026-09-27 로컬 화면을 직접 써 보고 정리했다.

- 메뉴가 13개다(대시보드, 실행 기록, 시나리오, 테스트 스크립트, 테스트 조건, 변경 기록, Hermes, API, API 호출, 테스트 데이터 만들기, 감사 로그, 가이드, 담당자). 무엇부터 해야 하는지 화면이 말해 주지 않는다.
- 대시보드 첫 화면에 표가 네 개 있다. 숫자는 많지만 "지금 내가 할 일" 이 없다.
- PR 을 검증하려면 사람이 여러 화면을 오가야 한다. dev 배포 목록 → 시나리오 → Hermes 케이스 채우기 → 케이스별 스크립트 만들기 → 실행 → 실패 분석. 각 단계가 따로 있고 이어 주는 흐름이 없다.
- 코드 id(`G.room.confirm#host-only`, `op.confirmRoom:E1410`)가 문장보다 앞에 나온다.
- 테스트 데이터 만들기 화면은 카드마다 설명·입력·Normal/Swagger·담당자·버튼이 한꺼번에 보여 길다.

## 3. 원칙

앞 설계의 원칙은 그대로 지킨다.

1. 실행 시작은 언제나 사람이다. PR 이 머지돼도 저절로 돌지 않는다. 플랫폼은 "검증 안 한 PR" 을 보여 주고 알림만 보낸다.
2. 모든 사람 행위는 감사 로그에 남는다.
3. 통과·실패 판정은 결정론 러너가 한다. Hermes 는 만들고, 고치고, 설명한다.
4. 스펙의 정본은 위키다. 플랫폼은 스펙을 고치지 않는다. 모호하거나 코드와 다르면 **질문을 만들어 사람에게 넘긴다.**
5. 검증 대상은 dev 다.

이번에 더하는 원칙:

6. **한 화면에는 한 가지 일.** 가장 중요한 버튼 하나만 파란색으로 크게 둔다.
7. **문장이 먼저, id 는 나중.** "방장만 진행을 확정할 수 있다" 를 먼저 쓰고 `G.room.confirm#host-only` 는 작게 뒤에 둔다.
8. **다음 할 일을 화면이 말한다.** 빈 화면, 기다리는 중, 실패 뒤에 무엇을 누르면 되는지 적는다.

## 4. 일 1 — Sanity 테스트 (PR 기준)

### 4.1 흐름

사람은 두 번만 누른다. PR 고르기, [Sanity 시작]. 그 뒤는 Hermes 와 플랫폼이 다섯 단계를 차례로 한다.

```text
[PR #138 고르기] → [Sanity 시작]  (사람)
  1. 관련 스펙 찾기     PR 변경 → API → 규칙표 → PRD 기능·시나리오
  2. 스펙 점검         모호한 곳 · 스펙과 코드가 다른 곳 · 없어진 API
        └ 사람이 정해야 할 것이 있으면 여기서 멈춘다 → [이대로 계속] 또는 [위키 고친 뒤 다시 점검]
  3. 테스트 조건·케이스 준비   새 스펙이면 채우고, 바뀐 스펙이면 다시 맞춘다
  4. 스크립트 만들기     자동으로 확인할 수 있는 케이스 중 스크립트가 없는 것
  5. 실행·검사         dev 에 실행 → 실패하면 Hermes 실패 분석
  → Sanity 결과  (PR 별로 남는다)
```

"실행 시작은 사람" 원칙과의 관계: [Sanity 시작]을 누른 사람이 다섯 단계 전체를 시작한 것으로 본다. 단계마다 담당자·시각·결과가 감사 로그에 남는다. 머지 이벤트로 저절로 시작하는 경로는 만들지 않는다.

### 4.2 단계별 내용

**1. 관련 스펙 찾기.** 플랫폼이 먼저 결정론으로 후보를 뽑고, Hermes 가 PR 본문·변경 요약을 읽고 고른다.

- PR 정보: GitHub 에서 제목·본문·변경 파일·커밋 메시지를 읽는다. 제목의 Linear 이슈 번호(MOI-541)도 쓴다.
- 결정론 후보: 변경된 컨트롤러의 경로 → API(operationId) → API 매핑 → 규칙표 명령·게이트 → 그 규칙의 출처 PRD 요구 id → 기능·시나리오. 도메인 폴더 이름(room, review …)도 후보에 넣는다.
- 백엔드의 결정 기록(`.worklog/*/decisions.md`)이 PR 에 있으면 근거로 함께 준다.
- Hermes 출력은 `{기능, 시나리오, 요구 id, 이유}` 목록이다. 플랫폼은 위키에 있는 기능·요구 id 만 받는다.

**2. 스펙 점검.** 두 가지를 합친다.

- 플랫폼 결정론 점검:
  - 스크립트나 API 매핑이 가리키는 API 가 dev API 문서에서 없어졌다.
  - 코드에는 있는데 API 문서에 없다(예: `PUT /v1/rooms/{roomId}`).
  - PRD·규칙표가 마지막 저장 뒤 바뀌었다(지금의 "PRD·규칙표 바뀜").
  - 규칙표에 없는 기능(예: 운영자 관리는 게이트·명령이 없다).
- Hermes 점검: PR 변경과 스펙 원문을 나란히 읽고 **모호한 곳**과 **스펙과 코드가 다른 곳**을 문장으로 낸다. 각 항목은 `{종류, 스펙 위치, 코드 위치, 무엇이 다른가, 사람에게 묻는 질문, 추천}` 이다.

찾은 것이 있으면 Sanity 는 **"스펙 확인 필요"** 로 멈춘다. 사람은 둘 중 하나를 누른다.

- [위키 고친 뒤 다시 점검]: 위키에서 PRD·규칙표를 고친 뒤 누른다. 2단계부터 다시 한다.
- [이대로 계속]: 사유를 적고 누른다. 모호한 항목에 걸린 케이스는 "사람이 확인" 으로 두고 나머지를 이어 간다.

질문 목록은 [Slack 으로 보내기] 버튼으로 기획 담당에게 넘길 수 있다(WIKI_SLACK_WEBHOOK_URL). 사람이 누를 때만 보낸다.

**3. 테스트 조건·케이스 준비.** 이미 있는 기능을 잇는다. 범위는 1단계에서 찾은 요구에 걸린 케이스와 그 시나리오의 정상 흐름이다. 시나리오 전체가 아니다(PR #138 이면 케이스 28개).

- 규칙표에서 나오는 테스트 조건은 위키가 바뀌면 저절로 바뀐다. 플랫폼은 무엇이 바뀌었는지 보여 준다.
- 규칙표로 적히지 않은 PRD 요구는 Hermes 가 "수동 작성 테스트 조건" 으로 제안해 저장한다(지금의 P4d).
- 시나리오 파일이 없거나 케이스가 빈 기능은 [Hermes 로 케이스 채우기]와 같은 방식으로 채운다.
- 지난 저장 뒤 바뀐 요구에 걸린 케이스는 [Hermes 로 다시 맞추기]와 같은 방식으로 고친다.
- API 가 없어진 케이스는 지우지 않는다. "스펙 확인 필요" 로 표시하고 2단계 질문에 묶는다.

**4. 스크립트 만들기.** 이번 범위의 케이스 중 자동으로 확인할 수 있는데 스크립트가 없는 것마다 Hermes 가 스크립트를 쓴다. 검증을 통과하면 바로 main 에 저장하고 "Hermes 작성" 표시를 단다(지금 규칙). 규칙표가 바뀌어 스크립트의 검증 항목이 낡았으면 [바뀐 테스트 조건에 맞게 스크립트 다시 쓰기](지금의 P4c)를 한다.

**5. 실행·검사.** 이번 범위의 스크립트를 dev 에 실행한다. 실행 종류는 `sanity`, PR 번호를 기록에 남긴다. 실패한 스크립트마다 Hermes 실패 분석(버그 · 스크립트 낡음 · 환경)을 붙인다.

### 4.3 Sanity 결과

PR 마다 한 장이 남는다. 맨 위에 한 문장으로 결론을 쓴다.

- 예: "스펙 확인이 2건 필요해요. 나머지 케이스 14개 중 13개가 통과했어요."
- 그 아래: 스펙 확인 필요 목록 → 바뀐 테스트 조건·케이스 → 새로 만든 스크립트 → 실행 결과(기능 · 시나리오 · 케이스로 묶어) → 실패 분석.
- [위키에 보고서 게시]는 지금처럼 사람이 누를 때만.

### 4.4 PR 목록

- GitHub 에서 dev 로 머지된 PR 을 읽는다(지금 "dev 배포" 목록의 출처와 같다).
- 상태: 검증 안 함 · 진행 중 · 스펙 확인 필요 · 통과 · 실패.
- 인프라·문서만 바꾼 PR(변경 파일이 `infra/`, `docs/`, `.github/` 뿐)은 "API 변경 없음" 으로 흐리게 두고 맨 뒤로 보낸다.

### 4.5 실제 예 — PR #138 (MOI-541)

오늘 이 설계를 쓰며 실제로 확인한 것이다. 2판이 있었다면 Sanity 가 찾았어야 할 항목이다.

| 종류 | 무엇 | 사람에게 묻는 것 |
| --- | --- | --- |
| 스펙과 코드가 다름 | 룸 취소 API(`POST /v1/rooms/{roomId}/cancellation`)가 지워졌다(DR-002). 방장이 나가면 위임하고, 후임이 없을 때만 취소된다. PRD 「룸 생성」 S2 `R147` 은 "모집 중인 룸을 취소한다" 가 그대로다 | PRD `R147` 을 백엔드처럼 "방장이 나가면 위임 또는 취소" 로 바꿀까요 |
| 스펙과 코드가 다름 | 진행 완료와 출석 기록이 나뉘었다(DR-003). 완료 뒤 방장이 출석을 한 번 기록한다. PRD 「룸 진행 마무리 및 출석」 S2 `R63` 은 "출석을 제출하면 완료된다" 다 | `R63` 을 "완료 뒤 출석 기록" 순서로 바꿀까요 |
| 모호함 | 확정 뒤 방장이 위임되면 모집 중으로 돌아가 다시 확정한다(DR-002). 「룸 진행 확정」에는 이 규칙이 없다 | 재확정 규칙을 규칙표에 넣을까요 |
| 코드에 있고 문서에 없음 | `PUT /v1/rooms/{roomId}`(룸 수정)가 컨트롤러에 있지만 dev API 문서에 없다 | REST Docs 에 추가를 요청할까요 |
| 영향 | 스크립트 `room.cancel`, `room.cancel-not-recruiting` 은 없는 API 를 부른다. 테스트 데이터 카드 "진행 시작 직전 상태의 룸" 은 MVP 에 진행 중 상태가 없어 쓸 곳이 없다 | 위 두 질문이 정해지면 Hermes 가 고친다 |

이번 작업에서 이미 고친 것: 정리 단계가 취소 API 를 쓰던 스크립트 3개를 dev QA 룸 삭제로 바꿨고, API 매핑에 진행 완료를 더했다(커밋 212bc36).

## 5. 일 2 — QA 데이터

지금 "테스트 데이터 만들기" 와 "QA 데이터 정리" 를 한 화면으로 합친다.

- 왼쪽 열: **만들기 목록**. 목적별로 묶는다.
  - 룸: 모집 중인 룸 · 신청이 들어온 룸 · 진행 확정된 룸 · 완료할 수 있는 룸
  - 계정·이력서: QA 회원 만들기 · 이력서 목록 보기 · 이력서 요약 완료
- 오른쪽 열: **지금 dev 에 남은 QA 데이터** 표(종류 · 이름 · 만든 때 · [지우기])와 [전부 지우기]. 전부 지우기는 가운데 확인 창에 목록을 보여 주고 확인을 받는다.
- 목록의 한 줄은 제목과 한 줄 설명만 보인다. 누르면 오른쪽에서 입력 패널이 열리고, 필요한 입력만 보인다. 기본값이 있으면 입력 없이 [만들기](⌘↵) 하나로 끝난다. 목록은 가려지지 않아 다른 카드로 바로 옮겨 갈 수 있다.
- 만든 뒤에는 같은 패널에 결과값(roomId 등)을 복사 버튼과 함께 보여 주고, [방금 만든 것 지우기]를 둔다.
- Normal · Swagger 보기는 패널 안의 "요청 원문 보기" 로 접어 둔다.

## 6. 일 3 — 스모크 테스트

- 왼쪽: 범위 표. **전체** · **기능별로 고르기** · **지난번 실패만** 중 하나를 고르고, 표에 기능별 스크립트 수·단계 수·지난 결과가 보인다.
- 오른쪽: 실행 패널. 고른 스크립트 수, 예상 시간, 실행 종류와 [스모크 실행]. 담당자 확인은 가운데 확인 창으로.
- 실행 중에는 진행 막대와 지금 도는 스크립트 이름을 보여 준다(지금의 SSE).
- 결과 첫 줄은 문장이다. "스크립트 16개 중 14개 통과, 2개 실패." 아래 표는 실패를 맨 위로 올리고, 실패 줄에 실패 이유와 Hermes 분석을 바로 적는다.
- 반복 실행(같은 스크립트를 n번 돌려 흔들림을 보는 것)은 아직 정하지 않았다(§10-5).

## 9. 데이터와 구현

### 9.1 새로 저장하는 것

- `sanity` 표: id, pr_number, pr_title, sha, status(queued · running · needs_spec · passed · failed · canceled), step(1~5), operator, created_at, finished_at, scope(JSON: 기능·시나리오·케이스), findings(JSON 목록), run_id, job_ids.

1. 화면 틀: 새 색·글꼴·버튼, 왼쪽 메뉴(주 메뉴 네 개와 관리 묶음), 홈. 기존 화면은 새 모양만 받는다.

4. Sanity 1: PR 목록, 관련 스펙 찾기, 스펙 점검, 멈춤과 계속.
5. Sanity 2: 준비 · 스크립트 · 실행을 잇고 Sanity 결과 화면.

- Sanity 실행 기록의 실행 종류는 새로 만들지 않고 `deploy-sanity` 를 쓴다(화면 이름은 "Sanity"). 옛 배포 검증 실행도 같은 이름으로 보인다.

### 13.1 확인한 사실

- 요청은 브라우저가 아니라 **플랫폼 서버가** 보낸다. 운영 플랫폼(qa.agent.plady.io, EC2)에서 `localhost:8080` 을 부르면 노트북이 아니라 EC2 자기 자신을 부른다. 노트북의 로컬 서버를 쓰려면 둘 중 하나다.
  - 로컬 서버를 터널(cloudflared · ngrok)로 공개 주소를 받아 등록한다.
  - 플랫폼을 노트북에서 띄운다(`python3 qa-platform/app.py`). 이때는 `localhost` 를 그대로 쓸 수 있다.
- 테스트 계정 토큰은 대상의 `POST /v1/auth/dev-sessions` 로 받는다. local·dev 프로파일에서만 열린다. live 는 막혀 있다.
- 테스트 계정(qa-host · qa-guest)은 dev DB 의 회원 id 다. 다른 서버의 DB 에는 그 회원이 없을 수 있다.
- 지금 토큰 캐시는 계정 이름으로만 저장한다. 대상이 둘 이상이면 섞인다(고쳐야 한다).
- 실행 기록에는 이미 대상 주소(`runs.base_url`)가 남는다.

### 13.2 제안

- **대상 목록**: dev 는 기본으로 늘 있다. [+ 대상 추가]로 이름·주소를 등록한다. 목록은 모두가 함께 쓰고(DB), 등록·삭제는 감사 로그에 남는다.
- **고르는 곳**: 왼쪽 메뉴 위에 "대상" 선택 상자. 고른 대상은 담당자별로 기억한다. 실행·API 호출·QA 데이터·Sanity 가 모두 그 대상으로 간다. 확인 창과 실행 결과에 대상을 크게 적는다. dev 가 아니면 주황 띠로 표시한다.
- **막는 것**: live 주소(`api.moimyeon.plady.io`)는 등록을 거절한다(고정 규칙: 검증 대상은 dev, live 와 무관). 운영 플랫폼에서는 내부 주소(localhost · 사설 IP · 169.254 · 도커 서비스 이름)도 거절한다. 서버가 자기 내부를 부르게 되는 것을 막으려는 것이다. 노트북에서 띄운 플랫폼에서는 localhost 를 허용한다.
- **등록 때 확인**: 그 주소의 `/actuator/health` 와 `dev-sessions` 를 한 번 불러 보고 결과를 보여 준다.
- **테스트 계정**: 대상마다 회원 id 를 따로 적을 수 있게 한다. 비우면 dev 와 같은 id 를 쓴다. 없으면 QA 데이터 화면의 [QA 회원 만들기]로 그 대상에 만든다.
- **토큰 캐시**: (대상, 계정) 으로 나눈다.

### 14.1 확인한 사실 (2026-09-28, 운영 서버에서 dry run)

- PRD(`raw/product/*.md`)는 고칠 수 있는 raw 다(wiki.toml `revisable`). `wiki_apply` mode `archive` 로 쓴다. dry run 통과.
- 규칙표 조각(`wiki/policy/_src/**.yaml`)은 `wiki_apply` 가 거절한다("slug cannot have a file extension"). `wiki_content_write`(asset 경로 `policy/_src/...`) 뒤 `wiki_content_commit` 으로 쓴다. 플랫폼 토큰으로 두 도구가 보인다. 둘 다 레지스트리의 approve 등급이다. 여기서 승인은 사람이 [위키에 반영]을 누르는 것이고, 감사 로그에 남는다.
- 위키 규칙: PRD 를 고치면 같은 작업에서 규칙표도 맞춘다. 조립본 `상태-SSOT.yaml` 은 고치지 않는다(EC2 렌더러가 조각이 바뀌면 다시 조립한다). 위키 CI 가 PRD 요구 줄의 변경과 그 요구를 인용한 규칙표 기록을 알려 준다.

### 14.2 흐름

```text
스펙 확인 항목 [추천대로] 또는 [다르게]+어떻게
  → 결정 기록 (지금과 같음)
  → Hermes 작업 "수정안 만들기" (사람이 누른 것으로 시작)
      근거: 항목(스펙·코드·질문·추천·결정), 그 기능의 PRD 전문, 규칙표 조각(기능/<PRD>.yaml, 필요하면 상태·공통)
      출력: 고칠 곳 목록 [{path, find, replace}] 과 한 줄 요약
  → 플랫폼 검증
      find 가 파일에 정확히 한 번 있는가 · 고칠 수 있는 파일인가(scope 기능의 PRD, _src 조각. 조립본 금지)
      PRD 요구 id 를 지우지 않았는가 · 조각을 바꾼 결과가 조립 검사(ssot_load check)를 통과하는가
  → 화면: 항목 아래 "수정안" — 바뀐 줄 비교, [위키에 반영] [버리기] [다시 만들기]
[위키에 반영] (사람)
  → 수정안을 만든 뒤 위키 파일이 바뀌었으면 거절하고 [다시 만들기]를 권한다
  → PRD 는 wiki_apply(archive) 한 번, 조각은 content_write 뒤 content_commit 한 번
  → 감사 로그 sanity.spec.apply(파일·커밋), 항목에 "위키에 반영됨"
  → 이어서 2단계부터 다시 점검 (반영을 누른 것이 곧 다시 점검의 시작)
```

- 수정안을 만들 수 없는 종류(없어진 API, API 문서 누락, 규칙표 없음)는 지금처럼 결정만 남긴다.

- 새 요구 문장이 필요하면 Hermes 는 그 PRD 에서 가장 큰 요구 id 다음 번호를 쓴다. 결정 근거로 `.worklog` 결정 id 와 PR 번호를 줄 끝 메모로 남기게 한다.

### 14.6 고친 것: 드리프트 경고와 수정안끼리 충돌 (2026-10-02)

운영에서 두 문제가 나왔다.

1. **반영하면 위키 CI 가 드리프트로 경고했다.** 위키 렌더러는 `index.yaml` 의 `meta.기준_문서[<PRD>]` 값이 바뀔 때만 sync-manifest 의 요구 문장 기준을 지금 PRD 로 옮긴다(render_wiki.py manifest). 수정안이 PRD 문장을 고치고 이 값을 안 올려서, CI(policy-drift-check)가 "문장이 바뀜" 으로 Slack 경고와 이슈를 냈다(a5c87c1, 위키 이슈 #2).
2. **같은 문서를 고친 수정안이 서로 막았다.** 찾아 바꾸기는 find 원문이 정확히 한 번 있어야 한다. Hermes 가 find 에 앞뒤 문맥을 넣으므로, 앞 수정안이 그 문맥을 바꾸면 같은 줄이 아니어도 뒤 수정안이 실패했다(예: 「룸 진행 확정」 R49). 사람은 [다시 만들기]를 눌러야 했다.

고친 내용.

- **기준 날짜.** 반영할 때 PRD 가 바뀌면 플랫폼이 `index.yaml` 의 그 문서 값을 반영 시각(KST, 분까지)으로 올려 같은 커밋 묶음에 넣는다. 이미 같은 값이면 초까지 적어 반드시 바뀌게 한다. Hermes 는 이 값을 고치지 않는다.
- **쓰는 순서.** 규칙표 조각 → PRD(`wiki_apply`) → `index.yaml` → `wiki_content_commit`. 렌더러는 조각 해시가 바뀔 때 디스크의 PRD 를 읽으므로, 기준 날짜는 PRD 를 쓴 뒤에 써야 새 문장이 기준이 된다.
- **위키 CI.** 커밋과 렌더 사이에 push 가 끼면 CI 가 렌더 전 상태를 본다. `check_policy_refs.py` 는 `index.yaml` 의 기준 값이 manifest 의 baseline 과 다른 문서를 "렌더 대기" 로 보고 문장 비교를 건너뛴다. 요구 id·절 검사는 그대로 한다(team-wiki-v2).
- **인용 기록.** 수정안을 만들 때 그 항목의 요구를 인용한 규칙표 기록(조각의 source `PRD/<문서> R<n>`)을 찾아 Hermes 에게 목록으로 주고, 그 기록이 있는 조각(`상태/*` 포함)도 고칠 수 있게 한다. 화면에는 PRD 문장이 바뀌는 요구마다 인용한 기록과 이번 수정안이 고친 기록을 보여 준다.
- **3-way merge.** 수정안을 만들 때 바뀐 파일의 원래 본문(base)과 고친 본문(after)을 `data/specfix/<sha>.txt` 에 저장한다. 반영할 때 지금 파일에 줄 단위 3-way merge 로 얹는다. 다른 줄이면 문맥이 바뀌어도 합친다. 같은 줄을 서로 다르게 고쳤을 때만 충돌이다. 저장본이 없는 옛 수정안은 찾아 바꾸기로 한다.
- **충돌하면 다시 만들기.** 여러 개를 반영할 때 충돌한 수정안은 빼고 나머지만 커밋한다. 충돌한 수정안은 플랫폼이 Hermes 에게 지금 위키 기준으로 다시 만들게 하고, 화면에 "다시 만들었어요, 확인 후 반영" 으로 보인다. 위키에는 사람이 다시 [위키에 반영]을 눌러야 쓴다. 감사 로그 `sanity.spec.conflict`.
- **남은 수정안 다시 계산.** 하나를 반영하면 같은 Sanity 의 대기 수정안은 지금 파일 기준으로 base·after·바뀐 줄을 다시 계산한다. 같은 줄이면 위처럼 다시 만든다.
- 시험: tests/test_specfix.py 7건(merge3, 기준 날짜, 인용 기록, 문맥이 겹친 두 수정안, 충돌 뒤 다시 만들기).

| ROOM_APPLICATION_SUBMITTED | 방장 | 웹 푸시, 닿지 않으면 메일 |
| ROOM_APPLICATION_ACCEPTED | 신청자 | 웹 푸시와 메일 둘 다 |
| ROOM_APPLICATION_REJECTED | 신청자 | 웹 푸시, 닿지 않으면 메일 |
| ROOM_CONFIRMED | 참여자 / 마감된 신청자 | 둘 다 / 웹 푸시, 닿지 않으면 메일 |
| ROOM_COMPLETED | 확정 참여자 | 웹 푸시, 닿지 않으면 메일. 출석·불참·후기 요청에 따라 본문이 다르다 |
| ROOM_CANCELED | 참여자, 취소한 방장, 마감된 신청자 | 둘 다 |
| ROOM_HOST_DELEGATED | 참여자 | 웹 푸시, 닿지 않으면 메일 |
| REVIEW_PUBLISHED | 후기 대상자 | 웹 푸시만. 1분마다 도는 작업이 공개 시각 뒤에 보낸다 |
| ROOM_COMMENT_POSTED | 작성자를 뺀 참여자 | 웹 푸시만 |

  "닿지 않으면" 은 등록된 기기가 없거나 모든 기기에 실패한 경우다.
- 보낸 기록을 남기는 곳이 없다. outbox 는 보내면 지워지고, 관리자 화면 `/admin/notifications` 는 대기 수와 실패(dead letter)만 보여 준다.
- dev 서버는 실제로 보낸다. 받는 주소를 바꾸거나 막는 설정이 없다. `POST /v1/dev/members` 로 만든 QA 회원의 메일은 `qa-<key>@qa.moimyeon.test` 라서 받을 수 없는 주소로 실제 발송된다. SES 반송률에도 좋지 않다.
- 웹 프론트(moimyeon-frontend main)에는 아직 FCM 토큰을 받는 코드가 없다. 생성된 SDK 에 등록 API 만 있다. 그래서 웹용 Firebase 설정값(apiKey, appId, VAPID 공개키)이 저장소에 없다.
- PRD 「회원 및 프로필」 §4.10 의 알림 수신 설정(R141~R163, MOI-544)은 백엔드 dev 에 아직 없다.
- SSOT 규칙: `P.notification.room_comment` · `room_canceled` · `room_host_delegated` · `room_recruiting_reopened` · `room_confirmed` · `receive_setting`, 그리고 `C.member.update_notification_setting`. 신청 접수·수락·반려, 완료, 후기 공개 알림은 PRD 문장에는 있지만 SSOT 규칙 기록은 없다.

### 15.2 받는 방법

**웹 푸시.** 플랫폼 안에 "수신기" 를 둔다. 수신기는 Firebase 에 웹 클라이언트로 등록해 FCM 토큰을 받고, 그 토큰을 QA 회원 이름으로 백엔드에 기기 등록한다. 이후 백엔드가 그 회원에게 보내는 웹 푸시가 수신기로 온다. 실제 사용자와 같은 FCM 경로다.

- 1안: 브라우저 없이 FCM 웹 클라이언트를 흉내 내는 라이브러리(Python `firebase-messaging`). 가볍다. Chrome 이 하는 등록 절차를 따라 하므로 Google 이 절차를 바꾸면 깨질 수 있다.
- 2안: 플랫폼 컨테이너에 화면 없는 Chromium(Playwright)을 두고, 플랫폼이 내주는 작은 페이지와 서비스 워커로 받는다. 실제 브라우저와 똑같다. 이미지가 수백 MB 커진다.
- 추천: 먼저 1안을 dev 로 시험하고, 안 되면 2안. 어느 쪽이든 필요한 값은 웹용 Firebase 설정(apiKey, appId, projectId, messagingSenderId, VAPID 공개키)이다. 공개해도 되는 값이지만 Firebase 콘솔에서 사람이 꺼내야 한다.
- QA 회원마다 수신기 등록이 하나씩 생긴다. 사람이 같은 QA 계정으로 브라우저에서 알림을 허용하면 그 기기도 함께 받는다.
- QA 회원을 지우면 백엔드가 기기 등록도 지운다. QA 데이터 화면에서 회원을 다시 만들면 수신기가 다시 등록한다.

**메일.** QA 회원의 메일 주소를 플랫폼이 읽을 수 있는 메일함으로 둔다.

- 추천: QA 전용 Gmail 계정 하나와 `+` 주소. 예: `moimyeon.qa+qa-host@gmail.com`. Gmail 은 `+` 뒤를 무시하고 한 메일함에 모은다. DNS 설정이 필요 없다. 플랫폼은 IMAP 으로 읽고, 앱 비밀번호는 SSM `qa-mail-app-password` 에 둔다.
- 다른 안: plady.io 하위 도메인에 Cloudflare 메일 전달을 켜고 전부 한 메일함으로 보낸다. 주소가 깔끔하지만 Cloudflare 설정이 필요하다.
- 백엔드 수정이 하나 필요하다. `QaMemberCreator` 의 메일 주소를 설정값으로 바꿀 수 있게 한다(예: `QA_MEMBER_EMAIL_TEMPLATE=moimyeon.qa+qa-{key}@gmail.com`). QA 회원 판별은 지금처럼 OAuth 식별자 접두어로도 하므로 도메인이 바뀌어도 정리 기능은 그대로다. 받을 수 없는 `qa.moimyeon.test` 로 보내던 문제도 같이 풀린다. 백엔드 레포 PR 은 사람이 리뷰한다.

### 15.3 저장

- `inbox` 표: 받은 알림 한 건씩. 채널(웹 푸시·메일), 받는 QA 회원, 대상 서버, 알림 종류(웹 푸시는 `data.eventType`, 메일은 제목으로 추정), 제목, 본문, 이동 주소, 받은 시각, 원본(JSON 또는 메일 원문), 맞춘 실행·단계.
- `receivers` 표: QA 회원과 대상 서버마다 웹 푸시 등록 상태(토큰, 등록 시각, 마지막 수신, 오류)와 메일 주소.
- 30일 지난 알림은 지운다. 실행 결과에 붙은 알림은 실행이 남아 있는 동안 둔다.

### 15.4 스크립트 단계

API 단계 뒤에 "알림 기다리기" 단계를 둔다. 새 단계 종류 `notify`:

```yaml
- name: 신청자에게 수락 알림이 웹 푸시와 메일로 온다
  notify:
    to: qa-guest
    type: ROOM_APPLICATION_ACCEPTED
    channels: [web_push, email]   # 둘 다 와야 통과
    within: 60s
    expect:
      title_contains: "{{roomTitle}}"
      link: /interviews/{{roomId}}
  covers: [C.application.accept]   # 알림을 일으킨 명령. 알림 규칙(P.notification.*)은 아직 테스트 조건이 아니다
- name: 댓글 작성자에게는 오지 않는다
  notify:
    to: qa-host
    type: ROOM_COMMENT_POSTED
    none: true
    within: 20s
```

- 기다리는 시간은 단계를 시작한 뒤부터 센다. 그 전에 온 알림은 보지 않는다.
- `none: true` 는 정한 시간 동안 오지 않아야 통과한다. 받는 사람 범위와 "작성자 제외" 같은 규칙을 검사한다.
- 후기 공개 알림은 후기 작성 3시간 뒤 공개될 때 간다. 바로 공개하는 dev 도구가 없어 스크립트로 기다리지 않는다(§16.11).
- 실행 결과의 단계 카드에 받은 알림을 보여 준다. 웹 푸시는 브라우저 알림 모양, 메일은 메일 모양 카드에 제목·본문·이동 주소·걸린 시간을 적는다. 실패하면 그 시간 동안 그 회원에게 온 다른 알림도 같이 보여 줘서 "다른 종류가 왔다" 와 "아무것도 안 왔다" 를 구분하게 한다.
- Hermes 가 스크립트를 만들 때 SSOT 의 `P.notification.*` 를 보고 알림 단계를 넣는다. 테스트 조건 정본은 지금처럼 SSOT 다.

### 15.5 화면: 알림함

왼쪽 메뉴에 **알림함** 을 더한다. 노트북 화면 기준 두 칸이다.

- 왼쪽 칸: QA 회원 목록. 회원마다 "웹 푸시 받는 중" · "메일 주소" 표시, 마지막으로 받은 시각. [웹 푸시 받기 켜기] 버튼 한 번으로 수신기 등록. 맨 위 "전체".
- 오른쪽 칸: 받은 알림 시간순. 위에 걸러 보기(채널, 알림 종류, 최근 10분·1시간·오늘). 새 알림은 몇 초 안에 위에 나타나고 잠깐 강조된다.
- 카드를 누르면 오른쪽 패널에 원본(웹 푸시 JSON, 메일 원문)과 이 알림을 맞춘 실행 단계 링크.
- 손으로 하는 QA 에 쓴다. dev 웹에서 QA 계정으로 무언가를 하고, 알림함을 옆에 띄워 두면 무엇이 언제 누구에게 왔는지 바로 보인다.
- 홈과 대상 서버 띠에 "웹 푸시 수신기 꺼짐" 같은 문제만 짧게 알린다.

### 15.6 규칙과의 관계

- 수신기는 받기만 한다. 알림이 왔다고 실행을 시작하지 않는다. 실행 시작은 지금처럼 사람이다.
- 수신기 등록, 해제, 메일함 설정 바꾸기는 사람 행위라 감사 로그 events 에 남긴다.
- 대상 서버가 dev 가 아니면(§13) 그 서버의 Firebase 프로젝트가 다를 수 있다. 처음에는 dev 만 지원하고, 다른 대상에서는 알림 단계를 "건너뜀(알림 수신 미설정)" 으로 보인다.

### 15.7 사람이 할 일

1. Firebase 콘솔 `moimyeon-development` 에서 웹 앱 설정값과 웹 푸시 인증서(VAPID 공개키)를 꺼내 준다. 프론트가 웹 푸시를 붙일 때도 같은 값이 필요하다.
2. QA 전용 Gmail 계정을 만들고 2단계 인증과 앱 비밀번호를 켠다. 앱 비밀번호는 SSM 에 넣는다.
3. 백엔드 `QaMemberCreator` 메일 주소 설정 PR 을 리뷰·머지한다. dev 환경변수에 템플릿을 넣는다.

### 15.8 순서

1. 시험: 1안 수신기로 dev 에서 QA 회원 하나에 웹 푸시를 실제로 받아 본다(댓글 작성 알림). 안 되면 2안.
2. 수신기와 `inbox` · `receivers` 저장, 알림함 화면.
3. 메일 수신(IMAP), 백엔드 PR.
4. 스크립트 `notify` 단계, 실행 결과 카드, Hermes 프롬프트.
5. 알림 수신 설정(R141~)이 백엔드에 들어오면 그 테스트.

### 15.9 정할 것

1. 웹 푸시 수신 방식: 1안 먼저(추천) / 처음부터 2안.
2. 메일함: QA 전용 Gmail `+` 주소(추천) / Cloudflare 하위 도메인 전달.
3. 백엔드 QA 회원 메일 주소 수정: 이번 작업에서 PR 까지 만든다(추천) / 백엔드 담당에게 맡긴다.
4. SSOT 에 없는 알림 규칙(신청 접수·수락·반려, 완료, 후기 공개): PRD 문장을 근거로 규칙 기록을 더하는 위키 수정안을 같이 만든다(추천) / 지금은 PRD 문장만 근거로 둔다.

### 15.12 메일함 결정 (2026-10-05)

사용자 결정: 앱 비밀번호 하나를 공용으로 쓴다. QA 메일함은 dev 백엔드의 Gmail 대체 발송 계정 `100dodukteam@gmail.com` 이고, 비밀번호는 백엔드가 이미 쓰는 SSM `/moimyeon/dev/core-worker/NOTIFICATION_EMAIL_GMAIL_APP_PASSWORD` 를 ec2-deploy 가 그대로 읽는다(같은 AWS 계정, 인스턴스 역할 AmazonSSMManagedInstanceCore). QA 회원 주소는 `100dodukteam+qa-{key}@gmail.com`(백엔드 dev 기본값).

알아 둘 것: 플랫폼은 팀 메일함 전체를 읽기 전용으로 훑고 `+` 주소로 온 메일만 담는다. SES 가 실패해 같은 계정이 Gmail 로 대신 보낸 메일은 받은편지함에 안 들어올 수 있어 놓칠 수 있다. 비밀번호를 바꾸면 백엔드와 플랫폼이 함께 바뀐다(다음 배포 때 읽는다).

### 15.13 백엔드 알림 수신 설정(moimyeon-backend #147, MOI-544)에 맞춤 (2026-10-05)

#147 이 `GET`·`PATCH /v1/members/me/notification-setting` 을 더하고 `DELETE /v1/members/me/web-push-subscriptions` 를 없앴다. worker 는 보내기 직전에 회원 설정을 보고 채널을 뺀다(웹 푸시를 못 받으면 PUSH_ELSE_EMAIL 은 메일, 둘 다 끄면 없음).

- 수신기 [웹 푸시 받기] 는 `PATCH {isWebPushAllowed: true, webPushRegistration: 토큰}` 으로 그 계정의 웹 푸시 수신을 켜고 등록한다. [끄기] 는 `PATCH {isWebPushAllowed: false}` 라 그 계정의 모든 기기 등록이 지워진다. 재시작 뒤 토큰이 바뀌면 `PUT` 으로 등록만 갱신한다(끈 계정이면 백엔드가 무시). #147 전 백엔드면 예전 등록·해제 API 로 되돌아간다.
- 스크립트 치환 `{{webpush.테스트 계정}}`: 켜 둔 수신기의 FCM 토큰. 스크립트가 웹 푸시를 껐다가 다시 켤 때 쓴다. 수신기가 꺼져 있으면 그 스크립트는 건너뛴다.
- 알림함은 계정마다 백엔드 수신 설정을 읽어, 웹 푸시나 메일이 꺼져 있으면 "수신 설정 꺼짐" 을 보인다.
- Hermes 스크립트 규칙: 설정을 바꾸는 스크립트는 `always: true` 정리 단계로 되돌린다.
- 알아 둘 것: 백엔드 QA 계정 초기화(`POST /v1/dev/members/{id}/reset`)는 알림 수신 설정을 되돌리지 않는다. 설정을 끈 스크립트가 정리 전에 멈추면 그 계정은 꺼진 채로 남는다.

### 16.2 1단계 — 플랫폼·AI 만으로 (백엔드 변경 없음)

1. **API 연결과 에러 코드를 AI 가 채운다.** Hermes 가 규칙표의 명령·검사마다 "어느 API 의 어떤 응답(코드)이 그 결과인가"를 API 문서(경로·설명·에러 예시)에서 찾아 제안한다. 플랫폼이 검증한다: operationId 가 API 문서에 있는가, 에러 코드가 그 API 의 예시에 있는가(없으면 공통 코드 E400·E1102·E1402 만 허용). 통과한 것은 `catalog/bindings.yaml` 에 바로 저장한다(Hermes 작성 표시, 지금 저장 흐름과 같다). 정본은 여전히 규칙표·API 문서이고 이 파일은 둘을 잇는 표다.
2. **에러 코드가 없어도 자동으로.** 케이스 채우기 규칙 "에러 코드가 없는 검사는 사람이 확인"을 바꾼다. 코드를 찾으면 그 코드로, 못 찾으면 "거절됨(4xx·result ERROR)"만 확인하는 스크립트로 만든다. 결과 화면에 "코드까지는 확인하지 않음" 을 표시한다.
3. **수동 이유를 나눈다.** 케이스의 `mode: manual` 에 이유를 단다: `no_api`(백엔드에 API 없음) · `needs_tool`(dev 도구 필요) · `structural`(구조상 일어날 수 없음) · `ui`(화면을 봐야 함). 플랫폼이 API 문서로 `no_api` 를 판정한다. 화면·홈·Sanity 의 "사람이 확인" 숫자에는 `ui` 만 센다. `no_api` 는 "백엔드 미구현" 으로 따로 모아 보여 주고, API 가 생기면(다음 Sanity·API 문서 다시 읽기) 저절로 자동 대상이 된다.
4. **한 번에 다시 판정.** 시나리오 화면에 [수동 케이스 다시 판정] 버튼. 사람이 누르면 Hermes 가 1·2 규칙으로 수동 케이스 전부를 다시 보고, 자동으로 바꿀 수 있는 것은 checks 를 채우고 스크립트까지 만든다. 실행 시작은 지금처럼 사람.
5. 알림 케이스는 알림 기다리기 단계로.

예상: 묶음 A 13 + D 1 이 자동으로, B 11 · E 1 은 "사람이 확인" 에서 빠진다. 사람이 확인 36 → 10(C 6 + F 4).

### 16.5 정할 것

1. 순서: 1단계 → 2단계 → 3단계(추천). 3단계는 1·2단계 뒤에 따로 설계 검토.

3. `bindings.yaml` 의 AI 연결: 검증 통과 시 바로 저장(추천, 지금 스크립트 저장과 같은 방식) / 사람이 승인.
4. 백엔드 미구현(`no_api`) 케이스: "사람이 확인" 에서 빼고 따로 보이기(추천) / 시나리오에서 지우기.

### 16.6 결정 (2026-10-06)

1. 1단계 → 2단계 순서로 진행. 3단계(AI 화면 확인)는 1·2단계 뒤 따로 설계 검토.
2. 에러 코드를 못 찾은 거절 케이스는 "거절됨(4xx·result ERROR)"만 확인하는 자동 스크립트로. 결과에 "코드까지는 확인하지 않음" 표시.
3. AI 가 찾은 API 연결·에러 코드는 검증 통과 시 바로 `catalog/bindings.yaml` 에 저장(Hermes 작성 표시).
4. 백엔드에 API 가 없는 케이스는 "사람이 확인" 에서 빼고 "백엔드 미구현" 으로 따로 보인다.

### 16.7 1단계 구현 (2026-10-07)

- `qa/binding_ai.py`: Hermes 가 API 연결·에러 코드·API 없음을 제안하면 플랫폼이 검증한다. operationId 는 API 문서에 있고 `/v1/dev/` 가 아니어야 한다. 에러 코드는 그 명령에 묶인 API 의 에러 예시에 있거나 공통 코드(E400·E1102)여야 한다. E1402 같은 검증 코드는 그 API 예시에 있을 때만 받는다. 통과한 것만 `catalog/bindings.yaml` 의 각 묶음 끝에 `# Hermes 날짜` 표시와 함께 더한다.
- `bindings.yaml` 에 `no_api` 묶음을 새로 둔다. 규칙표 명령인데 dev API 문서에 끝점이 없는 것을 이유와 함께 적는다. API 가 생기면 `commands` 로 옮긴다.
- 시나리오 목록 위 카드에 사람이 확인 · 백엔드 미구현 · dev 도구 필요 · 해당 없음 수를 따로 보인다. [수동 케이스 다시 판정] 버튼이 작업(`rejudge`)을 시작한다.
- 다시 판정 순서: API 연결 채우기 → `no_api` 명령을 가리키는 케이스는 바로 `no_api` → 나머지는 Hermes 가 auto 또는 수동 이유를 고른다. auto 는 API 가 묶인 테스트 조건이 있어야만 받는다. 저장은 시나리오마다 `revise` 로 하고 감사 로그 `scenario.rejudge` 를 남긴다.
- 설계 16.2-4 와 다른 점: 다시 판정은 스크립트까지 만들지 않는다. auto 가 된 케이스는 Sanity 나 케이스 화면의 [Hermes 로 스크립트 만들기] 로 만든다. 한 작업에서 케이스 수십 개의 스크립트를 한꺼번에 쓰면 실패 원인을 보기 어렵기 때문이다.

### 16.8 2단계 구현 (2026-10-07)

- 백엔드 PR moimyeon-backend#164: `POST /v1/dev/members/{memberId}/social-login`, `POST /v1/dev/members/social-signup`, `POST /v1/dev/members/{memberId}/status`, `POST /v1/dev/rooms/{roomId}/auto-complete`. 로그인 도구는 OAuth2 성공 처리에서 떼어 낸 `SocialLoginLander` 를 그대로 탄다. 탈퇴한 QA 회원이면 복구 확인 쿠키만 심는다.
- 실행기: 단계에 `cookie_jar: 이름` 을 달면 응답 Set-Cookie 를 그 이름의 저장소에 담고, 같은 이름의 다음 단계에 붙여 보낸다. 쿠키 경로가 요청 경로의 앞부분일 때만 붙인다. 만료된 쿠키는 저장소에서 뺀다. 쿠키로만 부를 단계는 `actor: null`. 쿠키 값은 기록하지 않고 이름·경로만 남긴다.
- `expect.cookies: {이름: set | cleared | absent}`: 그 응답이 쿠키를 심었나, 만료시켰나, 건드리지 않았나.
- 준비 카드: `setup.member-withdrawn`(새 QA 회원을 만들고 그 회원으로 탈퇴), `setup.member-restricted`(새 QA 회원을 만들고 이용 제한). 새 회원으로 부를 때는 `request.headers` 에 `Authorization: Bearer {{memberToken}}`.
- Hermes: 스크립트 만들기·케이스 채우기·다시 판정 프롬프트에 API 문서의 `/v1/dev/` 도구 목록을 넘긴다. 목록에 있는 일은 needs_tool 이 아니다. 백엔드 PR 이 배포되기 전에는 목록에 나오지 않으므로 판정이 바뀌지 않는다.
- 폼 편집기가 `cookie_jar` · `actor: null` · `request.headers` · `expect.cookies` · 상태 코드 `4xx` 를 지우지 않고 저장한다.

### 16.9 첫 다시 판정의 잘못과 보완 (2026-10-07)

운영에서 처음 돌린 다시 판정이 케이스 8개의 확인 대상을 다른 규칙으로 바꿨다. 신청 화면 진입 검사 5개를 신청 제출 검사로, 회원 쓰기 공통 규칙을 룸 생성·신청 규칙으로, 내 면접 로그인 검사를 API 계약 조건으로, 자동 완료를 완료·후기 규칙으로 바꿨다. 또 완료 알림 케이스를 "백엔드 미구현" 으로 잘못 판정했다(후기 요청은 완료 알림 본문에 들어간다).

- 8개는 원래 확인 대상으로 되돌렸다. 완료 알림은 알림 기다리기 단계로 확인하는 자동 케이스로, "일정 변경은 CS 문의" 는 해당 없음으로 바꿨다.
- 다시 판정은 확인 대상의 규칙(게이트·명령·API)이 바뀌는 checks 를 버린다(`_tc_owner`). 프롬프트에 알림도 플랫폼이 확인한다는 것과 checks 를 다른 규칙으로 바꾸지 말라는 규칙을 더했다.
- `bindings.yaml` 에 `gates`(명령에 묶이지 않은 게이트의 API)와 `client_side`(서버가 거절하지 않고 앱이 조회 응답으로 판정하는 게이트·명령의 설명)를 더했다. 신청 화면 진입은 룸 상세 응답의 `viewer` 로 확인한다. 스크립트 만들기 규칙 4가 이 설명을 받는다.
- 제외 규칙을 고쳤다. Google 가입·로그인은 dev 소셜 로그인·가입 도구로, 탈퇴는 실행마다 새 QA 회원으로 재현하므로 제외를 풀었다. 시스템 전이 제외에 `except: [C.room.autocomplete]` 를 두었다(자동 완료 dev 도구).

### 16.10 스크립트 실패 정리 뒤 보완 (2026-10-08)

- 자동 케이스라도 확인 대상이 모두 "API 없음" 명령이면 다시 판정이 "백엔드 미구현" 으로 옮긴다. 룸 수정·취소 8개, 후기 신고 정상 흐름 1개를 옮겼다. 이런 케이스는 예전 스크립트가 남아 있어도 상태가 "백엔드 미구현" 이고, 그 스크립트는 실행에서 빠진다.
- `bindings.yaml` 의 `gates` 에 `G.member.set_nickname: [updateProfile]`. 닉네임은 프로필 수정 API 로 바꾼다.
- 파일 업로드: 스크립트 단계의 `request.multipart` 로 보낸다. 파일 내용은 플랫폼이 만든 표본(pdf · pdf_oversize · text · empty)이고 기록에는 이름·크기만 남는다. API 문서의 multipart 필드는 Hermes 근거에 `multipart_fields` 로 들어간다(규칙 16).

### 16.11 알림 확인 바로잡기 (2026-10-09)

알림 기다리기 단계가 운영에서 한 번도 제대로 돈 적이 없었다. 기록된 단계는 수신기가 꺼져 건너뛴 것뿐이고, 건너뛰어도 스크립트가 통과로 끝나 눈에 띄지 않았다.

- 판정: 알림 확인을 건너뛰면 다른 단계가 모두 통과해도 스크립트는 skipped 다. 오류 칸에 "API 단계는 모두 통과, 알림 확인을 건너뛰었다" 와 이유를 적는다.
- 채널 일부만 받을 준비가 안 됐으면(예: 메일함 주소가 아닌 계정) 준비된 채널은 확인하고, 못 본 채널은 검증 항목에 ⏭ 로 남긴다. 준비된 채널에 알림이 안 오면 실패, 오면 스크립트는 skipped 다.
- 틀린 기대: 이동 주소가 `/interviews/{roomId}` 로 바뀌었다(백엔드 0fb9127b, 10-05). 완료 알림은 PUSH_ELSE_EMAIL 이라 웹 푸시만 기다린다(room.autocomplete · room.complete-notify). 진행 확정은 방장을 포함한 참여자 전원에게 웹 푸시와 메일이라 room.confirm 의 기대는 맞다.
- 발송 정책 표 `qa/inbox.py SENDS`: operationId 마다 알림 종류·받는 사람·채널. 백엔드 NotificationComposer 가 정본이다. Hermes 근거에 "이 API 가 보내는 알림" 절로 들어가고, 규칙 10 은 성공을 확인하는 스크립트에 알림 단계를 꼭 두게 한다.
- 알림 확인 빠짐: 성공하면 늘 알림을 보내는 API(신청 접수·수락·반려·진행 확정·완료·댓글)를 성공으로 확인하면서 그 알림을 기다리지 않는 스크립트는 정합성 검사 경고가 붙는다. [스크립트 한꺼번에 만들기] 가 지금 스크립트를 보여 주고 알림 단계만 더해 같은 id 로 다시 쓰게 한다. 다시 쓴 것에도 알림 단계가 없으면 저장하지 않는다. 나가기(방장 위임·취소·모집 재개)와 확정 때 대기 신청 마감은 조건이 맞을 때만 가서 경고하지 않는다.
- 스크립트로 못 보는 것: 후기 공개(작성 3시간 뒤). qa-host 메일(계정 메일이 메일함 주소가 아니다).
- 남은 것: 백엔드가 보내려 한 기록을 보는 dev 도구(`GET /v1/dev/members/{id}/notifications`)는 백엔드 PR 이 필요해 보류.
